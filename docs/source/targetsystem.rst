***************************
Target system specification
***************************
.. index:: pair: Targets; Overview

Prog8 targets the following hardware:

- 8 bit MOS 6502-family CPUs (6502, 6510, 65C02)
- 32 bit Motorola 68000/68020-family CPUs
- 64 KB address space on 6502 targets; much larger on M68K and virtual targets
- optional use of memory-mapped I/O registers
- optional use of system ROM routines

Currently these machines can be selected as a compilation target (via the ``-target`` compiler argument):

- 'c64': the Commodore 64
- 'cx16': the `Commander X16 <https://www.commanderx16.com/>`_
- 'c128': the Commodore 128
- 'pet32': the Commodore PET 4032
- 'amiga500': Amiga 500
- 'amiga1200': Amiga 1200 (68020 CPU with optional FPU)
- 'qemu68k': Qemu M68k simulator
- 'virtual': a builtin virtual machine (32-bit pointers, 16 MB memory)
- 'llvm64' (or 'llvm'): a hosted 64-bit program, compiled to LLVM IR (see :ref:`llvm_triples`)
- 'llvm32': a hosted 32-bit program, compiled to LLVM IR, such as WebAssembly with WASI
- 'llvm16': a 16-bit program, compiled to LLVM IR and built with `llvm-mos <https://llvm-mos.org/>`_ for the 6502, with llvm-z80 and z88dk for the Z80, or with llvm-mc6809 for the 6809 (experimental, see :ref:`llvm16`)
- custom targets via a separate configuration file (see :ref:`customizable_target`)

This chapter explains some relevant system details of the c64 and cx16 machines.
Details about the m68k targets are in the :ref:`amiga footnotes <amiga500footnotes>` below.

.. hint::
    If you only use standard Kernal and prog8 library routines,
    it is often possible to compile the *exact same program* for
    different machines (just change the compilation target flag)!

.. note::
    When you specify a file name as target, prog8 will try to read the target
    machine's configuration and properties from that configuration file instead.
    See :ref:`customizable_target` for details about this.


.. _customizable_target:

Customizable targets
====================
.. index:: single: Custom Targets; Overview

You can also specify a file name instead of one of the built in target machine names, when using the ``-target`` option.
In this case the compiler will not use one of the builtin machines configurations, but read it from the configuration file.
This allows you to define and change your own target machine configuration, and maybe allow Prog8 to generate
programs for new machines or existing ones it doesn't yet know about.

The configuration file should be a "properties" file (Java's ubiquitous configuration file format), which is basically a text file containing "key=value" lines.
The contents of the file is pretty extensive and it's easier to just look at some examples that are already included:
:source:`target configuration examples <examples/customtarget/>` .
The filename base part (the part before any suffix) of the target configuration file will be taken as the name of the compilation target.
If it matches one of the existing built-in compilation targets, the internal library files for that target will also be searched,
if the user supplied library location doesn't contain a replacement library file for anything that might get imported.
The path you need to provide for the ``library`` variable can be relative (to the current working directory where you launch the compiler from)
and you can use a tilde ``~`` in it like in a shell path, to refer to a user's home directory.
Library modules not unique to a specific compilation target (for example, `buffers`, `sorting` or `strings`) will
be picked up from the internal library files just fine as was always the case. You can still provide custom versions of them
in your own library folder of course, like you already could with using the ``-srcdirs`` compiler flag.

Most of the things discussed in the :ref:`portingguide` can and must be configured properly in the target configuration file.
You also need to create some essential ``syslib`` library module for the configured target if its name does not match
one of the built in targets. This is because the compiler won't have a built in library that can be used this time.
The customtarget examples also show how to build the essentials.

The target configuration file also allows you to override the entire launcher assembly fragment that the compiler
usually puts at the start of the program (immediately after the setting of the program counter/load address and
the program start label). This allows you to have full control over exactly what code or data bytes appear at
the program's load address. But with great power comes great responsibility: you'll have to make sure you take
care of some very low level Prog8 internals if you want to support stuff such as the ``exit`` builtin function.
Maybe the best thing is to look at the code generated by the compiler for an existing target and adapt that.

The ``launcher`` property lets you set the default launcher type for all programs compiled for this target,
without requiring a ``%launcher`` directive in every source file. Valid values are ``basic`` (CBM-BASIC SYS launcher)
and ``none`` (no launcher). If omitted, the default is ``basic``.

The optional ``pointer_size`` property sets the size of pointers in bytes. It defaults to ``2`` for compatibility
with existing configuration files. The supported values are ``2`` and ``4``.

.. _custom_target_m68k:

Custom targets for the 68000 CPU
--------------------------------

.. index:: single: Custom Targets; 68000

The compiler can also generate m68k code for a custom target machine, not just for the built-in
``amiga500``, ``amiga1200`` and ``qemu68k`` targets. The code generator is selected from the ``cpu``
property rather than from the target name, so declaring an m68k CPU is all that is needed to
route a custom target to the m68k backend.

Set the ``cpu`` property to the name of the CpuType enum value, ``M68000`` or ``M68020``::

    cpu = M68020

The exact spelling matters, because the value is the name of the enum value: write ``M68020`` and
not ``68020``. The 6502 CPUs are spelled ``6502``, ``65C02`` and ``virtual``, and those are tried
both with and without a ``CPU`` prefix, so ``6502`` and ``CPU6502`` both work.

An m68k target needs a much smaller configuration file than a 6502 one because it has no zeropage.
The M68K backend still uses compiler virtual registers internally, allocates them to hardware
registers, and spills values to memory when needed; this allocation is not configured in the target
file. The following zeropage-specific properties are not applicable and can be omitted:

* ``zp_scratch_ptr``, ``zp_scratch_b1``, ``zp_scratch_reg``, ``zp_scratch_w1``, ``zp_scratch_w2``
* ``zp_fullsafe``, ``zp_kernalsafe``, ``zp_basicsafe``
* ``virtual_registers``

These properties describe the 6502 zeropage layout and are ignored for an m68k CPU; a 6502 target
still requires them, and a typo there is still reported as a missing property. Set
``pointer_size = 4``, since m68k pointers are 32 bit.

Use ``output_type = ELF``. This is the only output type that links, and therefore the only one a
custom m68k target can use; the ``AMIGAHUNK`` output type assembles straight to an Amiga hunk
executable and is only available for the built-in Amiga targets. Two other things are worth knowing
when targeting bare metal: the FPU is enabled for the assembler regardless of the target, and the
assembler CPU is only upgraded to 68020 for ``amiga500`` with floating point enabled.

.. _custom_target_m68k_linker:

The linker script
^^^^^^^^^^^^^^^^^

An ``ELF`` output is produced in two steps: the compiler assembles to an object file, and then
links it into an ELF executable. The layout of that executable comes from a linker script, which
the compiler looks up in this order:

#. ``link.ld`` in the target's library directory (the directory named by the ``library`` property).
   This is how a custom target, which lives outside of the compiler, supplies its own memory layout.
#. ``/prog8lib/<targetname>/link.ld``, for targets that are built into the compiler.
#. ``/prog8lib/qemu68k/link.ld`` as a fallback, so a target without a script of its own still links.

A minimal script for a custom target looks like this::

    ENTRY(prog8_program_start)
    SECTIONS
    {
      . = 0x40000;
      .text : { *(.text) }
      .data : {
        . = ALIGN(4);
        *(.data)
        . = ALIGN(4);
        prog8_bss_section_start = .;
        *(.bss)
        *(COMMON)
        . = ALIGN(2);
        prog8_program_end = .;
      }
    }

``ENTRY`` should point at ``prog8_program_start``, the label the compiler emits for the start of
the program. The ``.data`` and ``.bss`` sections are deliberately merged into a single output
section so that the linker places them in one load segment. If ``.bss`` were its own output section,
the linker would compute that segment's address as "end of the previous segment + alignment" instead
of honouring the address in the script. Then ``prog8_program_end`` would no longer point at the true
end of the loaded image. For the same reason ``prog8_program_end`` is defined by the linker script
rather than by the generated assembly. Startup code that needs to clear the bss, such as the
``qemu68k`` bootinfo support, references that symbol, so leave it in.

The complete script used by the ``qemu68k`` target, together with a description of the linking
steps, is in :source:`the m68k linking documentation <codeGenM68k/docs/linking.md>`.

Source level restrictions
^^^^^^^^^^^^^^^^^^^^^^^^^

The m68k code generator rejects a number of directives and options that only make sense for a
6502 target: the ``%launcher``, ``%address``, ``%memtop`` and ``%varsaddress`` directives, split word arrays
written as ``&>``, and specific block addresses. Register annotations on ordinary subroutine parameters
are rejected as well; those are only used in ``asmsub``. The ``-varsgolden``, ``-varshigh`` and
``-varsaddress`` command line options are rejected as well, so where the variables are placed is
decided by the linker script instead.


.. _llvm_triples:

LLVM targets and triple profiles
================================

The ``llvm64``, ``llvm32`` and ``llvm16`` targets compile the program to LLVM IR, which clang then builds into an
executable for a particular platform, identified by its LLVM *target triple*. The target name fixes the
pointer size (8, 4 or 2 bytes); the ``-triple`` compiler option selects the platform, by naming a *triple profile*.
Without it, ``llvm64`` uses the built-in profile of the machine the compiler runs on (``arm64-apple-macosx``,
``x86_64-apple-macosx``, ``x86_64-unknown-linux-gnu``, ``aarch64-unknown-linux-gnu`` or ``riscv64-unknown-linux-gnu``,
and ``arm64-apple-macosx`` on any other machine), ``llvm32`` uses ``wasm32-wasip1``, and ``llvm16`` uses ``mos-sim``. So the same source gives
a different ``.ll`` file on different machines; pass ``-triple`` to build for a fixed platform.
Building needs clang 15 or newer, because the LLVM IR uses opaque pointers (the ``ptr`` type), which older
versions don't read. The compiler's tests run with clang 18 and newer.

With the default ``wasm32-wasip1`` profile, an ``llvm32`` program becomes a WebAssembly program for the WASI
system interface. Building it needs clang with ``wasm-ld`` (from lld) and the wasi-libc sysroot, given by the
``WASI_SYSROOT`` environment variable (default: the one of Homebrew's ``wasi-libc``); ``-emu`` runs it with
``wasmtime``, which gives it access to the current directory only. WASI programs start in the directory ``/``
of that sandbox, so the current directory has no host path there.

With ``-triple wasm32-unknown-emscripten``, an ``llvm32`` program becomes a WebAssembly program for Emscripten instead.
Building it needs clang and `Emscripten <https://emscripten.org/>`_, whose ``emcc`` is taken from the ``EMCC`` environment
variable, or else from the ``PATH``; clang compiles the program, and ``emcc`` links it into a single ``.js`` file with the
WebAssembly code inside. ``-emu`` runs that with ``node``. Unlike WASI, the program works with the host's own file system,
relative to the current directory, including creating, changing to and removing directories and renaming files;
it reads console input and gives back its exit status.
Emscripten's own clang and LLVM version don't matter, because ``emcc`` only links the object file.

With ``-triple armv7a-none-eabihf``, an ``llvm32`` program becomes a bare metal program for a 32-bit ARM Cortex-A15
with hardware floating point, which reaches the host through *semihosting*. Building it needs clang and the
`Arm GNU Toolchain <https://developer.arm.com/downloads/-/arm-gnu-toolchain-downloads>`_ for ``arm-none-eabi``
(on macOS: ``brew install --cask gcc-arm-embedded``), whose directory is given by the ``ARM_GNU_TOOLCHAIN`` environment variable
(default: ``/Applications/ArmGNUToolchain/15.3.rel2/arm-none-eabi``); clang compiles the program, and the toolchain's
``arm-none-eabi-gcc`` links it with newlib into a ``.elf`` file. ``-emu`` runs that on qemu's Versatile Express machine
(``qemu-system-arm``), which prints the program's output, gives its exit status back, and lets it read and write
files on the host, relative to the current directory. ``-emu`` stops a run after 60 seconds, because qemu keeps running
when the program crashes.

Newlib can't get console input from qemu by itself, so a small piece of console code that comes with the profile
(``startup_source``) reads it, a line at a time. qemu never reports the end of the input, so a Ctrl-D (character 4)
ends it, whether it is typed or piped in; without one, a program that reads all of its input waits for more until
the 60 second limit stops it. On a terminal, which qemu switches to raw mode, the console code echoes the typing
and handles backspace, and Enter ends the line. Ctrl-C stops qemu. Newlib on semihosting has limits:

- it has no ``mkdir``, ``chdir``, ``rmdir`` and ``getcwd``, so a program that uses the diskio routines to create,
  change to or remove a directory, or to get the current directory, fails to link ("undefined reference")
- renaming a file fails
- after a seek that fails, the position in the file is unknown, rather than left as it was
- a program argument can't contain a double quote, which the semihosting command line uses to keep spaces in an argument

With ``-triple riscv32-unknown-elf``, an ``llvm32`` program becomes a bare metal program for 32-bit RISC-V (RV32IMAFDC)
with hardware floating point, which also reaches the host through semihosting. Building it needs clang and the
`xPack GNU RISC-V Embedded GCC <https://xpack-dev-tools.github.io/riscv-none-elf-gcc-xpack/>`_, whose ``riscv-none-elf-gcc``
is taken from the ``RISCV_NONE_ELF_GCC`` environment variable, or else from the ``PATH``. clang compiles the program,
and ``riscv-none-elf-gcc`` links it with newlib, the console code and a small piece of boot code that come with the profile
(``startup_source``) into a ``.elf`` file. The boot code sets up the stack and switches on the floating point unit,
which newlib's startup code expects a loader to have done, passes on the semihosting command line, split as on ARM,
and lets the program's exit status reach qemu.
``-emu`` runs the program on qemu's virt machine (``qemu-system-riscv32``), with the same 60 second limit as on ARM.
Console input and newlib on semihosting work as on ARM, except that a seek that fails leaves the position in the file
as it was. The boot code passes on at most 60 arguments, and 1 KiB of command line.

The operating system owns the memory of an LLVM program, so anything that places the program or its variables
at a fixed address is an error on these targets: the ``%address`` directive (except on a profile with a ``load_address``,
such as ``mc6809-coco``), the ``%memtop`` and ``%varsaddress`` directives,
``%option romable``, ``%jmptable``, a block with an address, ``extsub`` with an address, and the ``-varsaddress``,
``-varsgolden`` and ``-varshigh`` options. Declare an external C routine as an ``extsub`` without an address instead.
The ``%output``, ``%zpreserved`` and ``%zpallowed`` directives and ``%zeropage full``, ``kernalsafe`` and
``floatsafe`` have no effect there and give a warning; ``%zeropage basicsafe`` and ``dontuse`` are accepted silently.
A ``%breakpoint`` inside a subroutine stops the program with ``llvm.debugtrap``; one at block level has no effect
and gives a warning. Native assembly code in ``%asm``, also as the body of an ``asmsub``, is an error: write the
code in ``%ir`` instead, or call an external C routine through an ``extsub``.

A scalar variable or parameter of a subroutine that only that subroutine uses, never by its address, lives in a
stack slot of each call instead of static storage, so LLVM can keep it in a register. ``@dirty`` and ``@shared``
variables, arrays, strings, and variables that another subroutine (such as a nested one) uses stay static.
A recursive subroutine that has only stack slots works; for one that keeps static storage, which its recursive
calls share, the compiler gives a warning that names those variables (not the arrays and strings that hold
literals, which are static on every target).

The ``examples/llvm`` directory has programs that use what these targets offer: input from a pipe with
``txt.eof()``, the command line, files and directories, recursion, ``uquad`` arithmetic, and calls of C library
functions through ``extsub``.

A triple profile is a "properties" file. ``-triple <name|file>`` looks for it in this order:

1. the given file path, when that file exists
2. ``~/.prog8/llvm/<name>.properties``
3. a profile built into the compiler: ``wasm32-wasip1``, ``wasm32-unknown-emscripten``, ``armv7a-none-eabihf``, ``riscv32-unknown-elf``,
   ``arm64-apple-macosx``, ``x86_64-apple-macosx``, ``x86_64-unknown-linux-gnu``, ``aarch64-unknown-linux-gnu``,
   ``riscv64-unknown-linux-gnu``, ``riscv32-unknown-linux-gnu``, ``armv7-unknown-linux-gnueabihf``, ``x86_64-pc-windows-msvc``,
   ``x86_64-w64-windows-gnu``, and for ``llvm16`` ``mos-sim``, ``mos-c64``, ``z80-test``, ``z80-trs80``, ``z80-trs80-cmd``,
   ``z80-trs80-m3-trsdos``, ``z80-trs80-m4``, ``z80-cpm``, ``z80-zx``, ``z80-c128``, ``mc6809-sim`` and ``mc6809-coco`` (``z80-z88dk`` is only a base, see ``base`` below)
4. any other triple that clang knows, such as ``aarch64-linux-musl`` or ``i686-unknown-linux-gnu``: the compiler asks
   clang for its normalized name, data layout and C ``long`` size, and builds with ``--target=<name>``.
   Run, link and startup settings need a profile file.

So you can add a platform, or change the settings of a built-in one, without rebuilding the compiler.
The Linux profiles and a triple from clang build on a host of that platform; cross compiling needs a sysroot and
a linker for it, given with ``-Xcompile`` and ``-Xlink`` or in a profile file, for example
``-Xcompile --sysroot=<dir> -Xlink -fuse-ld=lld``. The ``scripts/llvm-remote-check.py`` script runs the compiler's
llvm64 test programs on other hosts over ssh, built there or cross linked with a sysroot copied from them. The
``scripts/llvm-opt-check.py`` script runs the examples and test programs for llvm64 and on the virtual machine, each
optimized and with ``-noopt``, and reports the programs whose builds don't all give the same output.
``scripts/llvm-bench.py`` times benchmark programs built with and without ``-noopt``, as native llvm64 executables:
clang ``-O2`` turns both into the same machine code, so on these targets the Prog8 optimizer mainly saves compile time. ``x86_64-apple-macosx`` builds on any
Mac, and runs on Apple Silicon under Rosetta 2. ``x86_64-pc-windows-msvc`` builds with clang and the Microsoft C library,
where a C ``long`` has 4 bytes; its startup code switches the console and files to binary mode, so ``\n`` isn't written
as ``\r\n``, and adds the routines that the Microsoft C library lacks: ``usleep`` for ``sys.wait``, ``roundeven``, and the
directory routines for ``diskio.directory``. It is the default llvm64 triple on a 64-bit Windows host.
``x86_64-w64-windows-gnu`` builds with `llvm-mingw <https://github.com/mstorsjo/llvm-mingw>`_, whose clang must be the
``clang`` on the PATH; its startup code switches to binary mode and adds ``roundeven``, as mingw-w64 has the other routines.
On a Windows host, the compiler also needs the LLVM tools next to clang: the official LLVM installer leaves out
``llvm-as`` and some other tools, which the archive (``.tar.xz``) of an LLVM release has. A ``-o name`` without an extension
gets the extension ``.exe``. A wasm32 program needs clang's wasm32 runtime library, ``libclang_rt.builtins.a``, in
``lib/clang/<version>/lib/wasm32-unknown-wasip1`` of the LLVM installation; the Windows LLVM archive that this was tested
with didn't include it, so it had to be copied there from a build that has it.
These are the keys of a profile; an unknown key is an error:

``base``
    Another profile that this one is built on: it gets every key of the base that it doesn't have itself, and its own
    keys replace those of the base whole (a ``libc_lacks`` list is not merged, for instance). The base is a file path,
    relative to the directory of the profile that names it (``~`` is the home directory), then ``~/.prog8/llvm/<name>.properties``,
    then a profile built into the compiler; a built-in profile can only have a built-in base. A base can have a base
    of its own, but not in a cycle. The keys are combined before anything else, so a ``datalayout`` that neither one
    has still comes from clang. The profile keeps its own name, and ``base`` and ``abstract`` are not passed on.
``abstract``
    ``true`` for a profile that is only a base for other profiles, such as the built-in ``z80-z88dk``: using it with
    ``-triple`` is an error. The default is ``false``.
``triple`` (required)
    The LLVM target triple written into the module, for example ``wasm32-unknown-wasip1``.
``datalayout``
    The LLVM data layout string of that triple, as printed by ``clang --target=<triple> -S -emit-llvm -x c /dev/null -o -``.
    It starts with ``e`` for a little-endian or ``E`` for a big-endian target; on a big-endian target the bytes
    of a word or long in memory follow the machine's order (so ``@(&w)`` is the high byte of the word ``w``). Its pointer width (the ``p:`` entry, 64 bits when there is none)
    must match the target: 16 bits for ``llvm16``, 32 bits for ``llvm32``, 64 bits for ``llvm64``.
    Without it, clang supplies it for ``triple`` and ``clang_args``, which then must not need an unset environment variable.
``c_long_size``
    The size in bytes of the C ``long`` type on that platform: 4 or 8. Without it, clang supplies it like ``datalayout``.
``c_int_size``
    The size in bytes of the C ``int`` type: 2 or 4. Without it, clang supplies it when it is asked for ``datalayout``
    or ``c_long_size``, and otherwise it is 4.
``clang``
    The clang that builds for this profile: a name, looked up on the PATH like the other LLVM tools, or a path, such as
    ``${LLVM_MOS}/bin/mos-sim-clang``. Environment variables work as in ``clang_args``. The ``-clang`` option
    overrides it, and without either the compiler uses the clang it finds itself. llvm-as and llvm-ar are looked for
    next to the clang that is used first. A backslash starts an escape in a profile file, so write a Windows path
    with ``/`` or with doubled backslashes.
``clang_args``
    Extra arguments for clang when it builds the executable, separated by spaces, such as ``--target`` and ``--sysroot``.
    Environment variables can be used as ``${NAME}``, or as ``${NAME:-default}`` to use the default when the variable
    is not set; they only have to be set when clang is actually run.
``tool_path``
    Directories separated by spaces, put in front of the PATH of every program that is run for this profile: clang,
    llvm-as, the ``link_command`` and the ``run_command``. A program or ``clang`` given by name is looked up in them
    first. Environment variables work as in ``clang_args``, and a leading ``~`` is the home directory.
    For z88dk: ``tool_path = ${Z88DK}/bin``.
``tool_env``
    Environment variables as ``NAME=value`` pairs separated by spaces, set for the same programs, such as
    ``tool_env = ZCCCFG=${Z88DK}/lib/config``. Environment variables in the values work as in ``clang_args``.
    It can't set ``PATH``; that is what ``tool_path`` is for.
``output_extension``
    The file name extension of the built executable, such as ``.wasm``. Without it, the executable is named as usual on the host.
``link_command``
    A command that links the executable, for platforms that clang can't link for itself, such as bare metal ones
    with the C library of a GCC toolchain. clang then only compiles the program into an object file, which the command
    gets as ``{object}``, and it writes the executable to ``{file}``. ``{stem}`` is that path without the profile's
    ``output_extension``, for linkers that add their own extension, such as ``-o {stem}.bin``; the command must have
    ``{file}`` or ``{stem}``. Environment variables work as in ``clang_args``, and ``{profile_dir}`` is the directory
    of the profile file that has the ``link_command``, which can't be a profile built into the compiler.
    The libraries of the program's ``%link`` directives go at the end of the command, or in the place of a ``{libs}`` word.
    Without it, clang builds the executable in one go.
``link_args``
    Arguments at the end of the clang command that links the executable, after the libraries of the program's ``%link``
    directives, such as ``-lm``: the Linux profiles link glibc's math library this way. A profile with a ``link_command``
    can't have them; it puts them in that command instead. Environment variables work as in ``clang_args``.
``floats``
    ``true`` lets an ``llvm16`` program use floats, which are 32 bits there; without it a float variable, value or
    ``%import floats`` is an error. The 32- and 64-bit targets always have floats. The z80 profiles have it.
``c_double_size``
    The size of the C ``double`` that the C library's float formatting, parsing and math routines take: 8 (the default),
    or 4 where it is the same as a ``float``, as with z88dk's ``math32`` on the z80.
``float_source`` and ``float_link_args``
    Source files like those of ``file_source``, and words that a ``{floats}`` word in the ``link_command`` becomes, both
    only when the program uses floats (its LLVM IR has the ``float`` type), such as the float library: other programs
    don't grow by them. Without ``{floats}`` (and ``{startup}`` for the sources) in the link command, a program with
    floats doesn't link.
``float_digits_symbol``
    A C routine ``void f(char *buffer, double value)`` that writes the fewest digits that read back as the positive value,
    as ``snprintf``'s ``"%.*e"`` does, for ``floats.tostr()`` and printing; without it, ``snprintf`` and ``strtod`` find
    them, which needs both to be exact.
``defm_as_defb``
    ``true`` has clang write the program's assembly and then assemble it, with each ``DEFM`` string that has an octal
    escape before a digit 0-7 written as a ``DEFB`` list in between: z88dk-z80asm reads such an escape on into the digit,
    so llvm-z80's ``"\0001"`` (the bytes 0 and ``'1'``) became the one byte 1. The z80 profiles have it.
``last_drive_symbol``
    A C routine ``int f(void)`` among the ``file_source`` routines that gives the drive the last file open found or
    created its file on, or 255, for ``diskio.last_drive()``; a program that calls it gets the file sources linked.
    Without it, ``diskio.last_drive()`` is always 255. The TRS-80 profiles have it (``prog8_trs80_last_drive``), from
    byte 6 of the file's FCB.
``ticks_symbol`` and ``ticks_source``
    A routine ``unsigned int f(void)`` for ``sys.ticks()``, a count of 60ths of a second, and source files like those of
    ``file_source`` that are only built along with a program that calls it, before the ``startup_source`` files (so
    their initialization code runs first). Without ``ticks_symbol``, ``sys.ticks()`` is 0 on llvm16.
``getkey_source``
    Source files like those of ``file_source`` with ``int prog8_getkey(void)`` and ``int prog8_waitkey(void)`` for the
    llvm32 and llvm64 ``txt.getkey()`` and ``txt.waitkey()``, and ``int prog8_getchar(void)``, which ``txt.chrin()``
    then calls instead of ``getchar()``, and ``int prog8_termsize(void)`` for ``txt.width()`` and ``txt.height()``
    (the columns in the low byte and the rows in the high byte, or 0 for the default size); built along, first, only
    with a program that calls one of the key routines or the terminal size. Without it, both key routines are
    ``getchar()`` and the size is the default. The Unix and Windows profiles have it (``hosted-keys.c``).
``file_source``
    Source files like those of ``startup_source``, built along with the program only when it uses files (calls
    ``fopen()``, ``rename()`` or ``remove()``), such as the ``ftell``, ``fseek`` and ``fread`` of the TRS-80 profiles, which would otherwise make every
    program larger by the C library's file code that they call.
``startup_source``
    Source files separated by spaces, such as boot code in assembly, that the link command builds along with the program;
    a word ``{startup}`` becomes their paths. They are looked up next to the profile file that has the ``startup_source``,
    which can be a base, and else among those that come with the compiler, so a profile file can name a built-in one,
    such as ``z80-trs80-keyboard.asm``.
    A profile with it must have ``{startup}`` in its ``link_command``; without it, ``{startup}`` becomes nothing, so a
    base's link command can have it for the profiles built on it.
``load_address``
    The address the program loads at, as ``$3F00``, ``0x3f00`` or a decimal number, for a platform where the program can
    load anywhere. With it, the ``%address`` directive and the ``-address`` option set the program's load address, and
    ``{load_address}`` in the ``link_command`` becomes that address, as ``0x2500``; without it, both are errors.
``load_address_align``
    The number that a load address must be a multiple of, such as ``256`` for a whole page; ``1`` without it.
``link_script``
    A linker script template that is written next to the executable for the link, with ``{load_address}`` replaced by the
    load address; a word ``{link_script}`` in the ``link_command`` becomes its path. It is looked up as ``startup_source`` is,
    and a profile with it needs a ``load_address`` and ``{link_script}`` in its ``link_command``.
``run_command``
    The command that ``-emu`` uses to run the executable, with ``{file}`` in place of its path, for example ``wasmtime {file}``.
    Without it, the executable is run directly. The program arguments given after ``--`` go at the end of the command,
    or in place of a word ``{args}``; ``{semihosting_args}`` inside a word becomes the ``,arg=`` entries of qemu's
    ``-semihosting-config`` for the executable and its arguments, as in ``enable=on,target=native{semihosting_args}``.
    Environment variables work as in ``clang_args``, and ``{profile_dir}`` as in ``link_command``, for a runner script
    next to the profile: ``run_command = python3 {profile_dir}/run.py {file}``.
``program_args``
    ``false`` for platforms whose programs can't get command line arguments: giving them after ``--`` is then an error.
    The default is ``true``.
``run_timeout_seconds``
    The number of seconds after which ``-emu`` stops the run, for runners that can hang, such as an emulator after
    the program crashed. Without it, ``-emu`` waits until the program exits.
``strict_indirect_signatures``
    ``true`` for platforms that check the signature of a function called through a pointer, such as WebAssembly,
    which traps on any other. See below.
``c_main_symbol``
    The name that the C runtime of the platform calls the program's C ``main`` function by. The default is ``main``;
    wasi-libc calls it ``__main_argc_argv``.
``dirent_name_offset``
    The offset in bytes of ``d_name`` in the ``struct dirent`` that ``readdir()`` returns, which the diskio directory
    listings read. Without it, they fail: the bare metal profiles leave it out, as newlib has no directory routines.
``opendir_symbol``, ``readdir_symbol``
    The C library's names of ``opendir()`` and ``readdir()`` for that struct, when they differ from those, such as
    ``readdir$INODE64`` on Intel macOS and ``readdir64`` on 32-bit ARM Linux.
``fseek_symbol``, ``ftell_symbol``, ``file_offset_size``
    The C library routines that the file routines seek and tell the position in a file with, and the size in bytes of
    their offset. The defaults are ``fseek()`` and ``ftell()``, whose offset is a C ``long``. The Windows profiles name
    ``_fseeki64`` and ``_ftelli64`` with 8 bytes, because a C ``long`` has only 32 bits there.
``waitvsync_symbol``
    A C routine ``void f(void)`` that ``sys.waitvsync()`` calls, such as a wait for the raster's vertical blank in a
    support source. Without it, ``sys.waitvsync()`` waits one 60th of a second with ``usleep()``, or returns at once
    when the C library lacks that.
``wait_symbol``
    A routine ``void f(unsigned int jiffies)`` that ``sys.wait()`` calls instead of ``usleep()``, and ``sys.waitvsync()``
    with 1 when there is no ``waitvsync_symbol``; a ``ticks_source`` can have it, which is then built along with a
    program that calls it. ``z80-trs80-cmd`` has one that counts the ticks of ``sys.ticks()``.
``c_symbols``
    Other names for C functions that Prog8 calls, as ``name=symbol`` pairs separated by spaces, such as replacements in
    a support source for routines that the C library lacks or gets wrong: the TRS-80 profiles have
    ``fopen=prog8_trs80_fopen fread=prog8_trs80_fread fwrite=prog8_trs80_fwrite fputc=prog8_trs80_fputc``. Functions with
    a key of their own (``fseek``, ``ftell``, ``opendir``, ``readdir``, ``getchar``, ``putchar``) can't be named.
``getchar_symbol``
    The C library routine that reads the next console character, the way ``getchar()`` does, which is the default.
    The ``z80-test`` profile names ``fgetc_cons``, because ``getchar`` is a macro in z88dk. A profile that lists
    ``getchar`` in ``libc_lacks`` has no console input: reading a character gives 0, as at the end of the input.
``putchar_symbol``
    The C library routine that writes a console character, the way ``putchar()`` does, which is the default. It is
    called as ``int f(int)``. ``libc_lacks`` still names ``putchar`` itself.
``libc_lacks``
    The C functions, separated by spaces, that the platform's C library doesn't have, such as ``opendir readdir closedir``.
    Only the names of C functions that Prog8 programs can call are accepted.
``io_ranges``
    The memory-mapped I/O addresses, as comma-separated addresses and ranges in decimal or ``$`` hexadecimal,
    such as ``0-1,$d000-$dfff``, or ``*`` for every constant address that the machine has (below ``$10000`` on ``llvm16``; not the
    emulated cx16 registers).
``library``
    The name of a family directory of the target's embedded library, such as ``z88dk``, whose modules the compiler
    imports before the target's own; a project's own modules still come first. It is a plain name of letters, digits,
    ``_`` and ``-``. Without it, only the target's own library and the general one are searched.
``file_extension_separator``
    A character, other than ``.``, that replaces the last ``.`` of a file name before the C library's ``fopen``,
    ``remove`` or ``rename`` gets it, for a DOS whose file names have another separator. The program's string stays as
    it is: the name is copied to a buffer of 64 bytes, and a longer name is cut off. Without the key, names are passed
    as they are. ``z80-trs80-cmd`` sets ``/``.

The ``-Xcompile`` and ``-Xlink`` options add arguments to a single build without a profile of your own:
``-Xcompile`` arguments come after ``clang_args``, ``-Xlink`` arguments at the end of the ``link_command``, or at the
end of the linking clang command when the profile has none, but before the libraries of the ``%link`` directives. The ``.ll`` check with clang, when llvm-as isn't installed,
doesn't get them.

For example, the built-in ``wasm32-wasip1`` profile::

    triple = wasm32-unknown-wasip1
    datalayout = e-m:e-p:32:32-p10:8:8-p20:8:8-i64:64-i128:128-n32:64-S128-ni:1:10:20
    c_long_size = 4
    clang_args = --target=wasm32-wasip1 --sysroot=${WASI_SYSROOT:-/opt/homebrew/opt/wasi-libc/share/wasi-sysroot} -Wl,--fatal-warnings
    output_extension = .wasm
    run_command = wasmtime --dir=. {file}
    strict_indirect_signatures = true
    c_main_symbol = __main_argc_argv

**Indirect calls with strict signatures.** ``call(address)``, ``goto address`` and the other ways to run a routine
through its address call it without arguments. With ``strict_indirect_signatures``, they call it as a function
without a result, and a subroutine without parameters that returns a value is reached through a small entry
function that passes its result on, so ``call()`` and ``goto`` still give that value. Calling a subroutine with
parameters through its address traps, as does an address that isn't a subroutine.

**External C routines must have the exact C types.** An ``extsub`` without an address is declared with the widths
of its Prog8 types. On WebAssembly a mismatch with the C library's own type, such as ``uquad`` for the 32-bit
``size_t`` of wasm32, makes wasm-ld warn "function signature mismatch", and the call would then trap at runtime.
The built-in ``wasm32-wasip1`` profile passes ``-Wl,--fatal-warnings``, so such a mismatch fails the build instead.
On wasm32 the C ``int``, ``long`` and ``size_t`` types are all ``long`` in Prog8. A file seek to an offset that a 32-bit
C ``long`` can't hold fails.
A C function whose name starts with ``_``, such as picolibc's ``__decb_getc``, can't be declared as an ``extsub``,
as Prog8 identifiers can't start with an underscore: call it through a small C wrapper with another name, in a profile's
``startup_source`` (as ``mc6809-coco`` does for ``txt.getkey()``).


.. _llvm16:

The llvm16 target
-----------------

The ``llvm16`` target (experimental) compiles the program to LLVM IR for CPUs with 16-bit pointers, and builds it with
the `llvm-mos <https://llvm-mos.org/>`_ SDK for the 6502 family, or for the Z80 (see :ref:`llvm16_z80`) or the 6809 (see :ref:`llvm16_6809`). The
``LLVM_MOS`` environment variable names the directory of the llvm-mos SDK, whose clang the mos profiles use; building
fails without it, but writing the ``.ll`` file works. ``sys.target`` is 252.

``llvm16`` programs are optimized for size by default (``-Oz``, see the ``-O`` command line option): every function gets
the ``minsize`` and ``optsize`` attributes. Without them clang's inliner copies small routines into every call site
on the 6502 and the 6809 (llvm-mos and llvm-mc6809 inline much more readily than llvm-z80), and a program of some
size grows several times over: a 100-routine test program measured 44,773 bytes of code for the 6502 at ``-O2`` and
17,950 at ``-Oz``, 65,236 and 16,447 for the 6809, 14,078 and 11,673 for the Z80. A very small program can come out a
little larger at ``-Oz``. ``-O2`` gives speed back where it matters more than the memory.

The built-in profiles for the 6502 are:

- ``mos-sim``, the default: builds for the SDK's 6502 simulator, which ``-emu`` runs with ``mos-sim``. The simulator
  prints the program's output and gives back its exit status.
- ``mos-c64``: builds a Commodore 64 ``.prg`` file, which ``-emu`` starts in the VICE emulator ``x64sc``, in a window.
  Its startup source ``mos-c64-support.c`` has the ``usleep`` that the SDK lacks: ``sys.wait()`` waits that many ticks
  of the KERNAL's jiffy clock (``$A0-$A2``), which the interrupt advances 60 times a second on PAL and NTSC machines;
  with interrupts masked the clock stops, and it returns at once. ``sys.waitvsync()`` waits until the raster wraps
  around to line 0, as on the ``c64`` target (the profile's ``waitvsync_symbol``, ``prog8_c64_waitvsync`` in the same
  source).
  Its textio family ``c64`` (``prog8lib/llvm16/c64/textio.p8``) uses the 40x25 text screen at ``$0400``, with the lower
  case character set that the SDK switches on:

  - output goes through the SDK's ``putchar``, which turns ASCII into PETSCII for the KERNAL's ``CHROUT``, so
    ``print`` shows upper and lower case letters as they are; 128-255 go to ``CHROUT`` unchanged. ``{``, ``|``, ``}``
    and ``~`` show as the C64's graphics characters in their place. The control routines send ``CHROUT``'s own codes
    directly: ``cls`` 147, ``home`` 19, ``rvs_on`` and ``rvs_off`` 18 and 146.
  - ``plot`` and ``column`` move the cursor with the KERNAL's ``PLOT`` (``prog8_c64_plot`` in the support source);
    ``color`` sets the text color (``$0286``, 0-15). ``width()`` and ``height()`` give 40 and 25.
  - ``setchr`` and ``getchr`` use screen memory (``txt.SCREEN``), ``setclr`` color memory (``txt.COLORS``, ``$D800``).
    ``setchr`` puts ASCII 32-127 there as ``print`` shows them (``txt.screencode()`` converts), and 0-31 and 128-255
    as screen codes as they are (128-255 are reverse video). ``getchr`` gives the ASCII character back for screen
    codes 0-95, and the screen code itself for the others; 255 off the screen.
  - ``fill_screen`` fills screen and color memory and sets the text color; ``bell`` does nothing.
  - input: ``getkey`` and ``waitkey`` read the keyboard through ``GETIN`` (below); ``txt.chrin()`` and
    ``txt.input_line()`` read through ``CHRIN``, a whole line with the screen editor, which shows what is typed.

  Files go through the SDK's C library to the KERNAL. Its ``fseek`` needs an ``lseek`` that the C64 library doesn't
  have, so the profile lacks it: seeking, the file size and ``diskio.load`` report a failure. Its textio family ``c64`` reads the keyboard with the KERNAL's ``GETIN``.

Compared with ``llvm32`` and ``llvm64``:

- pointers have 2 bytes, as on the 6502 targets, a C ``int`` has 2 bytes and a C ``long`` 4.
- ``sys.set_irqd()`` and ``sys.clear_irqd()`` mask and unmask the CPU's interrupts, with ``sei`` and ``cli`` on the
  6502, ``di`` and ``ei`` on the Z80, and ``orcc #$50`` and ``andcc #$AF`` (IRQ and FIRQ) on the 6809, as inline
  assembly in the LLVM IR. On ``llvm32`` and ``llvm64`` they do nothing.
- floats are 32 bits, on the profiles with ``floats = true``: the z80 ones (see :ref:`llvm16_z80`). On the mos and
  6809 profiles they are not supported yet: a float variable, value or ``%import floats`` is an error.
- the programs get no command line arguments (``program_args = false``): ``sys.argc()`` is 0, ``sys.argv()`` is an
  empty string, and giving arguments after ``--`` is an error.
- ``sqrt`` of an integer is computed without floats.
- the value stack of ``push()`` and ``pop()`` has 256 bytes, instead of 1024.
- ``sys.memcopy``, ``sys.memset`` and ``sys.memsetw`` take a ``uword`` size; on ``llvm32`` and ``llvm64`` it is a
  ``long``, so more than 65535 bytes or words can be copied or set at once. On every llvm target ``memcopy`` copies
  overlapping areas correctly, in either direction.
- as on the other llvm targets, array indexes are words, so an array can have up to 65535 bytes, and ``%asm``,
  ``asmsub`` bodies and ``extsub`` with an address are errors (see :ref:`llvm_triples`).

**Real addresses.** Constant addresses such as ``@($d020)`` and ``@(0)`` access the machine's real memory; address 0
is not a null pointer here. A memory-mapped variable such as ``&ubyte border = $d020`` is at its real address when it
lies entirely below ``$10000``; others, such as the cx16 virtual registers ``cx16.r0`` to ``cx16.r15`` at ``$ff0000``,
remain ordinary variables. An access at a constant address, or at a memory-mapped variable plus a constant offset or
an index, is volatile when it touches an address in the profile's ``io_ranges`` (``$fff0-$ffff`` on ``mos-sim``;
the machine profiles such as ``mos-c64`` and the z88dk ones have ``*``, every real constant address), and so is any
access at address 0. Without that, clang may read such an address only once in a loop that makes no calls, and never
see a change that an interrupt makes, such as a clock or a cursor blink flag in the system's RAM. Accesses through pointers that are computed at
runtime are never volatile, so read and write I/O registers through constant addresses or memory-mapped variables.

**What the C library lacks.** The C library of llvm-mos has no math library, no ``strtod``, no ``usleep`` and no
directory routines, and the simulator has no files. The profiles list those routines in ``libc_lacks``, and the
library routines that need one behave as follows:

- files, on ``mos-sim`` only: opening a file fails, so the diskio and fileio routines that load, save, read, write,
  seek, delete or rename report a failure.
- directories: ``diskio.mkdir``, ``chdir`` and ``rmdir`` fail, and ``diskio.directory`` and its variants report a failure.
- ``diskio.curdir()`` returns an empty string.
- ``sys.wait()`` and ``sys.waitvsync()`` return immediately.
- ``math.atan2()`` is a compile error when the program can reach it, as it needs ``atan2f`` and ``floorf``.

An ``extsub`` of a C function that the library lacks doesn't link.

.. _llvm16_z80:

The Z80 with llvm-z80 and z88dk
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

The built-in ``z80-test`` profile (``-target llvm16 -triple z80-test``) builds for the Z80 with the clang of llvm-z80
and its ``z80-unknown-none-z88dk`` triple, which writes z88dk assembly. The ``zcc`` of `z88dk <https://z88dk.org/>`_
links the program with z88dk's C library for its ``+test`` platform, and ``-emu`` runs it in ``z88dk-ticks``, which
prints the program's output, reads its input, and gives back its exit status. It is built on the abstract
``z80-z88dk`` profile, which has what every z88dk platform shares: the triple, clang, data layout, sizes, ``tool_path``,
``tool_env`` and ``getchar_symbol``; ``z80-test`` adds the link and run commands and ``libc_lacks``. ``LLVM_Z80`` names the llvm-z80
directory and ``Z88DK`` the z88dk directory; the profile's ``tool_path`` and ``tool_env`` give the tools the PATH and
``ZCCCFG`` they need. As with the mos profiles, writing the ``.ll`` file works without them. The program is also linked
with ``lib/z80/z80_rt_z88dk.lib`` of llvm-z80: its compiler support routines (``__z80_memset_builtin``, ``__muldi3``
and others) built for z88dk, which llvm-z80's build installs.

Everything listed above for ``llvm16`` applies, except the real addresses: the Z80 has its own I/O ports, so the
profile has no ``io_ranges``, and the ``+test`` program itself starts at address 0. Besides:

- the I/O ports: ``sys.inp(port)`` reads a byte from one and ``sys.outp(port, value)`` writes one, through z88dk's
  ``inp`` and ``outp`` (``IN A,(C)`` and ``OUT (C),A``, with the whole 16-bit port in BC, as the ZX Spectrum needs).
  The 6502 and 6809 profiles have no I/O ports: they list ``inp`` and ``outp`` in ``libc_lacks``, so ``sys.inp``
  gives 0 and ``sys.outp`` does nothing.
- floats: 32-bit IEEE floats, through z88dk's ``math32`` library, whose C ``double`` is the same 32-bit float
  (``c_double_size = 4``); llvm-z80 calls its ``l_f32_`` routines for the arithmetic. The ``z80-z88dk`` base links
  ``--math32`` and its ``float_source`` ``z80-float.c`` only into a program that uses floats (``{floats}`` and
  ``{startup}`` in the link command), so the others stay as small. math32's ``printf`` gets about 7 digits right and
  its ``strtod`` is off in the last place, so ``z80-float.c`` has exact ones, with big integers: ``prog8_z80_ftoa``
  (``float_digits_symbol``) writes the shortest digits that read back as the float, as the other targets print them,
  and ``prog8_z80_strtod`` (``c_symbols``) reads the nearest float. Its ``floorf``, ``ceilf`` and ``roundevenf`` give
  0 and it has no ``tanf``, ``atanf``, ``atan2f`` and ``powf``, so ``c_symbols`` names its ``double`` routines for them
  and ``z80-float.c``'s ``roundeven``; the code generator calls a math routine that ``c_symbols`` renames instead of
  the LLVM intrinsic, whose name it couldn't change. The math routines are accurate to about 6 digits. math32
  compares a NaN as equal to itself, so ``f != f`` is false for a NaN, which converts to an integer as a large number
  instead of 0; ``floats.tostr()`` tells a NaN and infinity by their bits, so they print as ``NaN`` and ``Infinity``. A float is
  converted to text in a fraction of a second on a 4 MHz Z80, more for very large or small values. A program with
  floats is about 10 KB larger.

- console input works: the profile reads characters with z88dk's ``fgetc_cons`` (``getchar_symbol``).
- files: opening, reading, writing and seeking work on the host's files, but ``z88dk-ticks`` can't delete or rename a
  file, and its ``ftell`` always fails, so deleting, renaming, the file position and size, and loading a file into
  memory report a failure. z88dk's ``fread`` doesn't set the end of file, so ``fileio.eof()`` stays false after a read
  past it: stop reading when a read returns fewer bytes than asked. Directories, ``curdir()`` and waiting behave as on
  ``mos-sim``.
- the z88dk assembly format ignores alignment, so a ``memory()`` slab is not aligned; clang warns about it, and also
  prints a harmless "cannot compile inline asm" warning.
- ``z88dk-ticks`` prints a ``Ticks:`` line with the number of cycles when the program exits.

For a Z80 machine without a built-in profile (see :ref:`llvm16_z80_platforms`), write a profile of your own with ``base = z80-z88dk`` that links for another z88dk platform, for example
``link_command = zcc +zx -create-app -o {stem}.bin {object} -l${LLVM_Z80}/lib/z80/z80_rt_z88dk`` with ``output_extension = .tap`` for the
ZX Spectrum, with that platform's ``libc_lacks``.

``scripts/z88dk-profile.py <platform> [subtype] [--clib NAME] [-l LIB ...] [-o FILE]`` writes such a profile (it needs
``Z88DK``), for example ``scripts/z88dk-profile.py cpm -o ~/.prog8/llvm/z80-cpm.properties``. It reads the platform's
configuration in z88dk's ``lib/config``, refuses subtypes and C libraries for other CPUs (8080, Game Boy, Rabbit,
eZ80) and z88dk's new and sdcc C libraries, and links small probe programs with ``zcc`` to work out the link command,
the ``output_extension`` (the ``-create-app`` file, or the plain binary when that file isn't named after the ``-o``
name, as on CP/M) and the ``libc_lacks`` of functions that don't link. When the C library needs a malloc heap to link,
the link command gets ``-pragma-define:CRT_HEAP_AMALLOC=1``, a heap of 3/4 of the free memory, and also
``-pragma-define:CRT_HEAP_ENABLE=1`` when the platform's crt0 can then end the heap at the system's top of memory
(the TRS-80's HIGH$), as the heap otherwise ends at the stack pointer. Check by hand what a
link can't show: ``io_ranges``, ``getchar_symbol``, ``program_args``, a ``run_command``, and functions that link but
misbehave on the platform, which belong in ``libc_lacks`` too.

.. _llvm16_z80_platforms:

**Built-in Z80 machine profiles.** These profiles are built on ``z80-z88dk`` like ``z80-test``, and link for a real
machine with z88dk's classic C library. They have no ``run_command``, so build the program with ``-o`` and load the
output file into the machine or an emulator yourself:

=======================  ===========================  ==========  ===================  ============
Profile                  ``zcc`` platform             Output      ``io_ranges``        Arguments
=======================  ===========================  ==========  ===================  ============
``z80-trs80``            ``+trs80``                   ``.cas``    ``*``                no
``z80-trs80-cmd``        ``+trs80 -subtype=cmd``      ``.cmd``    ``*``                yes
``z80-trs80-m3-trsdos``  ``+trs80 -subtype=cmd``      ``.cmd``    ``*``                yes
``z80-cpm``              ``+cpm``                     ``.com``    none                 yes
``z80-zx``               ``+zx``                      ``.tap``    ``*``                no
``z80-c128``             ``+c128 -subtype=disk``      none        ``*``                no
=======================  ===========================  ==========  ===================  ============

What ``z80-test`` lists above applies to them as well, except the file notes, which are about ``z88dk-ticks``. All of
them lack the directory and ``usleep`` functions, and ``qsort`` because z88dk's calls the comparison
function with its arguments swapped. All but ``z80-trs80-cmd`` and ``z80-trs80-m3-trsdos`` also lack ``free``, ``realloc`` and ``strdup``, as
their C library has no malloc heap. The programs
that the compiler's tests build for ``z80-test`` also build for these profiles. The tests also run them for CP/M in
tnylpo and, when ``TRS80GP`` names the trs80gp binary, for the TRS-80 in trs80gp (Model III with LDOS and with TRSDOS 1.3, and a few on
the Model I and 4, and as ``.cas`` files from ROM BASIC without a DOS). They do that through test profiles in
``compiler/test/fixtures/llvm-triples``, built on ``z80-cpm``, ``z80-trs80-cmd``, ``z80-trs80-m3-trsdos`` and ``z80-trs80``, whose support sources mirror the console output where the runner script can catch
it (the TRS-80 printer) and pass on the exit status (a last output line on CP/M, as tnylpo always exits with 0).

**The z88dk and trs80 textios.** ``z80-zx`` sets ``library = z88dk``, and ``z80-trs80`` and ``z80-trs80-cmd`` (and
``z80-trs80-m3-trsdos``, based on it) ``library = trs80``, with ``putchar_symbol = fputc_cons``: all console output goes
through z88dk's generic console, and ``txt`` comes from ``prog8lib/llvm16/z88dk/textio.p8`` or
``prog8lib/llvm16/trs80/textio.p8`` instead of the ANSI one. The two have the same routines, from
``shared_z88dk_console_textio.p8``, and differ in their constants: ``DEFAULT_WIDTH`` and ``DEFAULT_HEIGHT`` (64 by 16 on
the TRS-80) and the key codes (see the keyboard input below); the ``trs80`` module is only in the trs80 family. Its routines are those of the llvm16 ``txt``, plus
``getchr`` and ``setclr``. ``cls``, ``home``, ``plot``, ``column``, ``setchr`` (which leaves the cursor where it was),
``width`` and ``height`` work everywhere; ``getchr`` reads the screen with z88dk's ``cvpeek``, and ``setclr``
rewrites the character it reads there in the new ink. ``color``, ``setclr``, ``setcc``, ``rvs_on`` and ``rvs_off``
send the generic console's ink and inverse codes, which only do something where the platform has them: the ZX
Spectrum does, the TRS-80 has neither colour nor inverse video. ``bell`` does nothing. ``z80-cpm``
and generated profiles keep the ANSI textio on standard output; a generated profile can add the two keys for a
platform that has z88dk's generic console. Its routines are listed in
`skeletons-llvm16-z88dk.txt <_static/symboldumps/skeletons-llvm16-z88dk.txt>`_ and
`skeletons-llvm16-trs80.txt <_static/symboldumps/skeletons-llvm16-trs80.txt>`_.

**The z88dk-ansi textio.** ``z80-c128`` sets ``library = z88dk-ansi`` and ``putchar_symbol = fputc_cons``: all
console output goes through z88dk's ANSI console, and ``txt`` comes from ``prog8lib/llvm16/z88dk-ansi/textio.p8``,
with the same routines as the z88dk textio. ``cls``, ``color`` and ``rvs_on`` send the ANSI sequences of the llvm16
textio, ``rvs_off`` sends ``ESC[27m`` (``ESC[0m`` would also reset the colour to white). ``color`` takes the ANSI
colours 0-7 (black, red, green, yellow, blue, magenta, cyan, white), which the console shows as the C128 colours 0, 2,
5, 7, 6, 4, 3 and 1. ``plot``, ``home``, ``column`` and ``setchr`` use z88dk's ``gotoxy``, ``width`` and ``height``
its ``screensize`` (40 by 25). ``getchr`` reads the screen memory at ``$2000`` and gives back the character that was
printed there, without its reverse video; it doesn't use ``cvpeek``, as linking that replaces the C128 font with one
without lower case. ``setclr`` writes the colour memory at ``$1000``, so it keeps the character, the cursor and the
colour of ``color``; ``setcc`` is ``setchr`` and ``setclr``. ``fill_screen`` and ``clear_screenchars`` fill the two
memories directly. ``bell`` does nothing. The console puts a character code on the screen as the screen code of the
C128's upper and lower case font, only moving the lower case letters and the codes above them down by 96: so ``@``,
``[``, ``\``, ``]``, ``^`` and ``_`` show as graphics, and the backquote, ``{``, ``|``, ``}`` and ``~`` as ``@[£]↑``.
The profile links with ``-pragma-define:ansicolumns=40``: without it z88dk's console is 64 columns wide, so ``width``
gives 64 and positions past column 39 land on the next line. The routines are listed in
`skeletons-llvm16-z88dk-ansi.txt <_static/symboldumps/skeletons-llvm16-z88dk-ansi.txt>`_.

A program can call more of z88dk's C library through an ``extsub`` without an address. llvm-z80 calls a C function
the way z88dk's own "smallc" convention expects: the arguments pushed from left to right as 16-bit words, the caller
removing them, the result in L or HL. So routines such as ``gotoxy(unsigned x, unsigned y)``, ``wherex()``,
``cvpeek(int x, int y)``, ``screensize(unsigned *w, unsigned *h)``, ``getk()`` and ``kbhit()`` can be called directly
(declare a C ``int`` or ``unsigned`` as ``word`` or ``uword``). Routines declared ``__z88dk_fastcall`` (their single
argument in HL, such as ``textcolor``) or ``__z88dk_callee`` (the ``*_callee`` versions, which remove their own
arguments) can't be called this way; use the console control codes instead, or a small assembly wrapper.

For machine-specific screen code, such as writing to the TRS-80's video RAM at ``$3c00``, put a ``textio.p8`` of
your own next to the program (or in a ``-srcdirs`` directory): the compiler looks there before it looks in its
built-in library, so that file replaces ``txt`` for the program. Keep the routine names of the built-in one, so
the rest of the library still finds what it uses.

**Use** ``txt.width()`` **and** ``txt.height()`` **for the screen size, not** ``txt.DEFAULT_WIDTH`` **and**
``txt.DEFAULT_HEIGHT``. With the z88dk textio those constants are 80 and 25, as one library serves all its machines,
while the screen is 32 by 24 on the ZX Spectrum. ``txt.width()`` and ``txt.height()`` ask z88dk for the real size.
(The textio of a single machine has its own: 64 by 16 with the trs80 textio, 40 by 25 with the z88dk-ansi textio of the
C128 and the c64 one, 80 by 24 with the trs80m4 one, 32 by 16 with the coco one; ``txt.COLUMNS`` and ``txt.ROWS`` are the
same with the last three.) Screen code of your own that computes a video RAM
address from ``DEFAULT_WIDTH``, such as ``$3c00 + row * DEFAULT_WIDTH + col`` on the TRS-80, reads and writes the
wrong place from the second row on.

**Keyboard input on llvm16.** Every llvm16 textio has ``txt.getkey()``, which gives the key pressed or 0 when there is
none, without waiting, and ``txt.waitkey()``, which waits for a key and gives it. What they use depends on the textio:

- the llvm16 textio (``mos-sim``, ``z80-test``, ``mc6809-sim`` and generated profiles), where the console is a stream:
  ``waitkey`` is ``txt.chrin()``, the next character of stdin, so it gives 0 at the end of the input. There is no
  keyboard polling: the C libraries of these profiles can't read stdin without waiting, so ``getkey`` always gives 0.
  ``txt.input_line()`` doesn't echo what it reads: a terminal shows what is typed itself.
- the c64 textio (``mos-c64``): ``getkey`` is the KERNAL's ``GETIN`` (the SDK's ``cbm_k_getin()``), which gives the next
  key typed (PETSCII) or 0, and ``waitkey`` calls it until it gives a key; ``txt.chrin()`` and ``txt.input_line()`` read
  through ``CHRIN``, a whole line with the screen editor.
- the cpm textio (``z80-cpm``) is that stream textio with key routines of its own: ``getkey`` is BDOS function 6 with
  ``$FF`` (in the profile's startup source ``z80-cpm-keyboard.asm``), which gives the next key typed or 0, and ``waitkey`` is
  ``txt.chrin()``, z88dk's ``fgetc_cons()``, the same BDOS call until it gives a key; at the end of the input tnylpo
  gives ``^Z`` forever (26). z88dk's own ``getk()`` isn't used: it reads keys until none is left and gives the last.
- the z88dk, trs80 and z88dk-ansi textios (``z80-zx``, ``z80-trs80``, ``z80-trs80-cmd``, ``z80-c128``): ``getkey`` is z88dk's
  ``getk()`` (``int getk(void)``) and ``waitkey`` is ``txt.chrin()``, z88dk's ``fgetc_cons()`` (``int fgetc_cons(void)``),
  which waits for a key and doesn't echo it. On the TRS-80 ``getk`` calls the ROM's keyboard scan (``$002b``), which reports
  a new key press; on the ZX Spectrum it takes the ROM's last key (``LAST-K``) and clears it; on the C128 it scans the
  keyboard matrix and gives the key that is held down, again on each call while it is held, as ``in_Inkey()`` does
  (``in_Inkey()`` gives the key held down now, ``getk()`` on the other platforms the next key press). Enter is the
  platform's code, 13 on the TRS-80 and the C128, unless z88dk's ``STANDARDESCAPECHARS`` is on. z88dk's TRS-80 library
  is built with it, which turns Enter into 10, the code of the down arrow, so the TRS-80 profiles link their own
  ``getk`` and ``fgetc_cons`` from the startup source ``z80-trs80-keyboard.asm`` (``-pragma-redirect`` in the link
  command): they give the ROM's codes, Enter 13, down 10, up 91, left 8, right 9 and CLEAR 31, also to ``txt.chrin()``.
  Letters come in lower case unshifted and as capitals shifted on the Model I and III alike: the Model III ROM's caps
  lock (``$4019``) is off during each scan and put back after it, and the Model I ROM's capitals are swapped. The
  ``trs80`` module (``prog8lib/llvm16/trs80/trs80.p8``, ``%import trs80``) has ``caps_lock(bool)`` for capitals
  unshifted, ``model()`` (1 or 3), ``dos()`` (``DOS_NONE``, ``DOS_TRSDOS``, ``DOS_LDOS``), ``has_lowercase()`` (false on a
  Model I without the lower case kit) and ``capitals(bool)``, which makes the profiles' ``fputc_cons`` (redirected to
  ``_prog8_trs80_console`` in the same source) show lower case letters as capitals. The Model 4 profile's ``trs80``
  module gives ``model()`` 4 and ``dos()`` ``DOS_6``.
- the trs80m4 textio (``z80-trs80-m4``): ``getkey`` is ``@KBD``, which gives the key typed or 0, and ``waitkey`` is
  ``txt.chrin()``, ``@KEY``, which waits for a key. Enter is 13, the left arrow and backspace 8, the right arrow 9 and
  BREAK 128; letters come as typed (lower case unless shift or caps lock).
- the coco textio (``mc6809-coco``): ``getkey`` calls Color BASIC's ``POLCAT`` (picolibc's ``char __decb_getc(void)``,
  through the wrapper ``int prog8_coco_getkey(void)`` in the profile's startup source), which reports each key press
  once, and ``waitkey`` calls it until it gives a key. Enter is 13 there, while ``txt.chrin()`` (picolibc's ``getchar``,
  which polls ``POLCAT`` too) gives it as 10. Both read the same keyboard, so a key goes to whichever reads first.

On the machine profiles (the z88dk, z88dk-ansi, trs80m4 and coco textios) the key routines don't echo, so ``txt.input_line()``
(and ``input_chars``, ``readln`` and ``prompt``, which use it) echoes each character it stores through ``txt.chrout()``,
and a new line at Enter, as BASIC does. Backspace (8, the CoCo's and the TRS-80's left arrow; 12 and 127 are taken as
it too, the delete key of the ZX Spectrum and the C128) removes the last character from the screen and the buffer.
Other control codes, and the characters past the maximum length, are ignored. There is no end of the input there.

**Key codes.** The keys whose codes differ between the machines have constants in every llvm ``txt``, for
``getkey()`` and ``waitkey()``: ``KEY_UP``, ``KEY_DOWN``, ``KEY_LEFT``, ``KEY_RIGHT``, ``KEY_ENTER``, ``KEY_ESC``,
``KEY_BACKSPACE`` and ``KEY_BREAK``. Letters, digits and other printable keys need none: a character literal such as
``'a'`` is the code of the key everywhere. A key that the machine lacks gets a code that no key there gives, the same one
for that key on every machine (248 up, 249 down, 250 left, 251 right, 252 escape, 253 backspace, 254 break), so the
constants of one textio all differ and can be the choices of a ``when``:

On the CoCo and the TRS-80 the left arrow is also the backspace of ``txt.input_line()``, so ``KEY_BACKSPACE`` is the
code of a missing key there. ESC is shift and the up arrow on the TRS-80, EDIT on the ZX Spectrum; the C128's Z80 mode
key scan has no codes for the cursor keys. CP/M has the WordStar keys (Ctrl-E, Ctrl-X, Ctrl-S, Ctrl-D), as its
terminals differ. The llvm16 stream textio's ``waitkey()`` reads lines from stdin, so Enter is its line end, 10.

**Keyboard input on llvm32 and llvm64.** ``txt.getkey()`` gives the key pressed or 0 when there is none, without waiting
and without echo, for programs such as editors that read single keys, and ``txt.waitkey()`` waits for a key and gives
it, or 0 at the end of the input. On Unix it switches a terminal on stdin to a raw
mode at its first call: no echo, no line editing, and no signals, so Enter gives 13 and Ctrl-C 3 (and Ctrl-Z 26) instead
of ending or stopping the program; DEL (127) is given as backspace, 8. Output keeps its processing, so ``"\n"`` still starts a new line. The terminal goes
back to its own mode when the program ends, and while ``txt.chrin()`` or ``txt.input_line()`` (and ``input_chars``,
``readln`` and ``prompt``) read, which echo and edit the line as usual; the next ``getkey`` makes it raw again. On
Windows it is the console's ``_kbhit()`` and ``_getch()``. The cursor keys' escape sequences (``ESC [ A`` and ``ESC O A``,
also with modifiers such as ``ESC [ 1 ; 5 A``) become the PETSCII cursor codes of the Commodore targets: 145 up,
17 down, 29 right and 157 left; on Windows the console's cursor keys do too. Other escape sequences come as their bytes,
one per call, and ``ESC`` alone, with nothing after it within 30 milliseconds, as 27. When stdin isn't a terminal or a
console, ``getkey`` reads its next byte, waiting for it, and gives 0 at the end of the input. The wasm and bare-metal
profiles have no such keyboard: there ``getkey`` and ``waitkey`` are ``txt.chrin()``. A program that only uses
``txt.chrin()`` and ``txt.input_line()`` is built as before, without this code.

**The terminal's size on llvm32 and llvm64.** ``txt.width()``, ``txt.height()`` and ``txt.size()`` give the size of
the terminal window that stdout writes to, at the moment of the call, as on the cx16 they give the current screen
mode's: on Unix from ``ioctl(TIOCGWINSZ)``, on Windows the visible window of the console. When stdout isn't a terminal
(a pipe or a file), and on the wasm and bare-metal profiles, they give ``txt.DEFAULT_WIDTH`` and
``txt.DEFAULT_HEIGHT`` (80 by 25), so a program whose output is piped always sees the same size. Each is at most 255.
Nothing is read from stdin for this, and nothing waits. ``txt.size_changed()`` is true when the window now has another
size than one of these routines last found, so a program such as an editor can check now and then (between keys, with
``txt.getkey()``) whether to lay out its screen again. ``txt.clear_screenchars()`` and ``txt.fill_screen()`` fill the
current size. ``txt.DEFAULT_WIDTH`` and ``txt.DEFAULT_HEIGHT`` stay constants, for array sizes.

**A clock on llvm16.** ``sys.ticks()`` counts 60ths of a second (``sys.TICKS_PER_SECOND``, the unit of ``sys.wait()``)
in a ``uword``, which wraps around after about 18 minutes: take the difference of two counts. When it starts counting
and how often it changes depend on the machine, and it is 0 where there is no clock:

- ``mos-c64``: the KERNAL's jiffy clock (``$A1``-``$A2``), 60 a second.
- ``mc6809-coco``: Color BASIC's ``TIMER`` (``$0112``), 60 a second.
- ``z80-zx``: the ROM's ``FRAMES`` (23672), 50 a second, in 60ths: it goes up by 1 or 2.
- ``z80-trs80-m4``, under TRSDOS 6 and LS-DOS 6: an interrupt task of the DOS, in a module named ``P8TICKS`` that the
  first program that asks for the time puts below HIGH$ (and below ``$f400``, where the DOS pages in the keyboard and
  screen; with HIGH$ above that, the memory up to HIGH$ stays unused). It stays there until the next reboot, and later
  programs find it with ``@GTMOD``, so a program that ends in any way leaves no task behind. Task slot 11 runs 60 times
  a second; when it is taken, slot 8 or 9 runs 30 times a second and adds 2.
- ``z80-trs80-cmd`` under LDOS 5.3 on the Model III, and under LDOS 5.3 and TRSDOS 2.3 on the Model I: the same
  module, in task slot 8, 9 or 10, which run at every interrupt: 30 times a second on the Model III, adding 2, and 40
  on the Model I, adding 1 and 2 in turn. These DOSes have no ``@GTMOD``: the program finds the module through the task
  table at ``4500H``, and calls ``@ADTSK`` at ``403DH`` (Model III) or ``4410H`` (Model I). 0 under TRSDOS 1.3
  (``z80-trs80-m3-trsdos`` too), which has no interrupt tasks. ``sys.wait()`` waits by this clock (``wait_symbol``),
  and ``sys.waitvsync()`` until its next tick; without the clock both return at once.
- 0 on ``z80-trs80`` (the ``.cas`` file), ``z80-cpm``, ``z80-c128`` and the simulators (``mos-sim``, ``z80-test``,
  ``mc6809-sim``).

The DOS keeps interrupts off while it reads or writes a disk, so the TRS-80's count can fall behind during disk I/O.
On llvm32 and llvm64 ``sys.ticks()`` comes from C11's ``timespec_get()``, the time of day in 60ths of a second, also
in a ``uword``; 0 on the bare metal ARM and RISC-V profiles, whose C library lacks it.

- ``z80-trs80``: the TRS-80 Model I and III, as a cassette file. The program starts at ``$5200``. The Model I has
  memory-mapped devices at ``$37e0-$37ff`` (the printer at ``$37e8`` and the disk controller), both models the
  keyboard matrix at ``$3800-$3bff`` and the video RAM at ``$3c00-$3fff``; the Model III has its printer on port
  ``$f8`` instead. Without a DOS the file routines are stubs that fail. Load the ``.cas`` file with ``SYSTEM``
  from cassette: enter the name (its first six letters) or its first letter, and ``/`` to start it once it is loaded.
  The program's stack starts at the top of memory, which it reads from ROM BASIC's MEMSIZ (``$40b1``), so it fits
  the machine's RAM size (checked with 16 and 48 KB).
- ``z80-trs80-cmd``: a ``.cmd`` program for TRSDOS or LDOS on the Model I and III, started from the DOS prompt, which
  passes its command line. The TRS-80 profiles' startup source ``z80-trs80-command-line.asm`` copies the command line
  for z88dk's startup code, which parses a byte before it (the last letter of the program's name, or of its drive spec,
  became ``argv(1)``), and gives no command line when the program doesn't get one, like one that trs80gp loads and
  starts (where z88dk's code wrote a 0 into the DOS, after which ENTER no longer worked). The file routines go through z88dk's TRSDOS library. Its ``ftell`` doesn't link, its
  ``fread`` never sets the end of the file, and its ``fseek`` only moves forward with ``SEEK_CUR`` and ignores the
  offset with ``SEEK_END``, so the profile's ``file_source`` (``z80-trs80-files.c``) has an ``ftell``, ``fseek`` and
  ``fread`` of its own (``ftell_symbol``, ``fseek_symbol``, ``c_symbols``), and an ``fsync`` that succeeds, as
  z88dk's always fails, which made ``fflush`` fail. Its ``ftell`` reads the position of a file being read from the
  DOS's file control block. TRSDOS 2.3 and LDOS keep the position of a file being written differently there, so the
  source's ``fopen``, ``fwrite`` and ``fputc`` count the bytes written instead, in three bytes of the ``FILE`` that
  z88dk doesn't use; for a file open for both ``ftell`` gives -1. A seek past the end of a file being read fails, and
  a file being written only seeks to where it is. Seeking forward reads the file to the position, and seeking back
  rewinds it through the DOS and reads it from its start, so it is slow in a large file. z88dk's appending (mode ``"a"``) reads to the end of the file and writes from there, which
  under TRSDOS 2.3 on the Model I writes garbage after the old end, so the source's ``fopen`` opens an existing file
  for reading, reads it to the end for its size, lets the DOS position to the end, and then writes there.
  z88dk's ``remove`` opens the file without a sector buffer to delete it, which fails under TRSDOS 2.3, so the source
  has a ``remove`` of its own. z88dk has no ``rename``, and no DOS call renames a file, so the source's ``rename``
  copies the file to the new name and deletes the old one: it needs room on the disk for the copy, the new file
  gets no password and the date of the rename, and renaming fails when the new name exists. A DOS file name is
  ``NAME/EXT``, where a ``.`` would start the file's password, so the profile's ``file_extension_separator`` turns
  the last ``.`` of a file name into ``/``: ``memory.prg`` becomes ``MEMORY/PRG`` for the DOS. The DOS's limits of
  8 characters for the name and 3 for the extension still apply. The link command gives the malloc heap the memory from the end of the program to
  HIGH$ (``-pragma-define:CRT_HEAP_AMALLOC=1 -pragma-define:CRT_HEAP_ENABLE=1``); the library's ``open`` allocates
  each file's FCB and buffer there, and ``strdup``, ``realloc`` and ``free`` need it. Without ``CRT_HEAP_ENABLE``
  the heap would end at the DOS's stack, below the program, and wrap into the ROM, so every ``fopen`` fails. The
  program returns to the DOS prompt when it ends. In the trs80gp emulator, ``trs80gp -m3 -ld prog.cmd`` boots LDOS
  on a Model III and runs it (``-m1`` is a Model I). There, writing files works on the Model III LDOS disk; the
  Model I TRSDOS 2.3 boot disk is write-protected (``-im wp 0 off`` lifts that) and the Model I LDOS boot disk
  has no free space.

  TRSDOS 1.3, the default DOS on the Model III, starts a program with its stack at ``$4089``, in the system's
  variables. z88dk's startup code puts 64 bytes on it for ``atexit``, which moves the stack down onto those
  variables, and the program hangs before ``main``. Use ``z80-trs80-m3-trsdos`` there (below).
- ``z80-trs80-m3-trsdos``: ``z80-trs80-cmd`` for the Model III with TRSDOS 1.3. The link command puts the stack at
  HIGH$, which the Model III keeps at ``$4411`` (``-pragma-define:REGISTER_SP=-0x4411``), so it fits the machine's
  RAM size and what the DOS keeps in high memory, and the malloc heap ends below the stack (no ``CRT_HEAP_ENABLE``).
  Files work as with ``z80-trs80-cmd``, but TRSDOS 1.3 keeps a different record number in the file control block,
  which ``-DPROG8_TRS80_TRSDOS13`` in the link command makes the file source follow. Programs also run on the Model
  III with LDOS, where ``fileio.tell`` and ``fileio.seek`` of a file being read are then wrong, but not on the
  Model I, whose HIGH$ is at ``$4049``. In trs80gp, some programs hang when they create or open a file under
  TRSDOS 1.3, as the DOS aborts to its prompt while loading an overlay; the cause is not known yet. In trs80gp, ``trs80gp -m3 prog.cmd`` boots TRSDOS 1.3 and runs it.

- ``z80-trs80-m4``: a ``.cmd`` program for the TRS-80 Model 4 in its own mode, with TRSDOS 6 or LS-DOS 6, on its 80x24
  screen. z88dk has no Model 4 target (its TRS-80 support is for the Model I and III memory map, and its file routines
  call Model I/III DOS entry points that TRSDOS 6 doesn't have), so the profile links for ``+trs80`` without the TRSDOS
  library (``-subtype=disk``), at ``$3000``, and its startup source ``z80-trs80-m4.asm`` uses the DOS's supervisor
  calls (``RST 28H``): the stack moves to HIGH$, but below ``$f400``, as the display and keyboard routines page the
  screen and keyboard into ``$f400``-``$ffff`` while they run; console output goes through ``@DSP``, and ``getk`` and
  ``fgetc_cons`` through ``@KBD`` and ``@KEY``; the program ends through ``@EXIT`` with its exit status in HL, after the
  rest of z88dk's exit code (which would close the files). Its other startup source ``z80-trs80-m4-wait.c`` has the
  ``usleep`` for ``sys.wait()`` and ``sys.waitvsync()``: ``@PAUSE``, whose count takes about 17 microseconds (measured
  on trs80gp's Model 4). ``PROG A B`` and ``PROG:1 A B`` give ``sys.argc()`` 3, with ``A`` and ``B``; ``argv(0)``,
  the program name, is empty, as z88dk's TRS-80 startup code doesn't set it. ``library = trs80m4`` gives ``txt`` the trs80m4 textio
  (``prog8lib/llvm16/trs80m4/textio.p8``): ``plot``, ``getchr`` and ``setchr`` through ``@VDCTL``, reverse video
  through the display codes 16 and 17 (``getchr`` gives a reversed character with bit 7 set), ``cursor_on`` and
  ``cursor_off`` through 14 and 15, ``get_cursor`` through ``@VDCTL``, ``bell`` through ``@SOUND``, 80 columns and
  24 rows, and no colors. Display code 21 doesn't switch to an alternate character set. Of the video control port
  ``$84``, which ``sys.outp`` writes and which the DOS keeps a copy of at ``$0078`` (update both), bit 2 selects
  64x16 instead of 80x24 characters and bit 3 shows characters 128-255 as inverse video instead of graphics and
  special characters (as ``rvs_on`` does); bits 0 and 1 select the memory map, 5 and 7 locked up the DOS, and 4 and 6
  showed no change (checked in trs80gp). Files go through the DOS too: z88dk's file routines are stubs
  there (``-lndos``), and the profile's ``file_source`` (``z80-trs80-m4-files.c``) has ``open``, ``close``, ``read``,
  ``write``, ``readbyte``, ``writebyte``, ``lseek``, ``fdtell``, ``remove`` and ``rename`` in their place, and an
  ``fread`` (``c_symbols``) that sets the end of the file, which z88dk's never does, with byte I/O
  through ``@GET`` and ``@PUT`` on the DOS's file control block and its sector buffer. The position and the size come
  from that control block, so ``fileio.tell`` and ``seek`` work for files being written too; a seek moves to the
  record (``@POSN``) and reads its way to the byte, and can't go past the end of the file. Mode ``"w"`` removes an
  existing file and creates it anew, as the DOS can't shorten one; ``"a"`` positions to the end (``@PEOF``).
  ``diskio.rename`` is the DOS's ``@RENAM``, which fails when the new name exists. A new file without a drive spec goes
  to the first drive, which must have room: the DOS doesn't try the next one. There are no subdirectories, so
  ``mkdir`` and ``rmdir`` fail, but ``diskio.chdir(":1")`` makes drive 1 (0 to 7, when it is ready: ``@CKDRV``) the
  current drive, which ``diskio.curdir()`` gives as ``":1"``: file names without a drive spec then get ``":1"`` (to open,
  create, delete and rename them), and ``diskio.directory`` lists that drive. ``chdir("")`` (or ``":"``) goes back to no
  current drive, as at the start. ``diskio.directory`` lists the files of the current drive (else drive 0), sorted by name
  with their sizes: the file source's ``opendir``, ``readdir`` and ``closedir`` read the directory "." through ``@RAMDIR``
  (``dirent_name_offset = 0``), and its ``qsort`` (``c_symbols``) sorts, as z88dk's calls the comparison with the
  arguments swapped. In trs80gp,
  ``trs80gp -m4 prog.cmd`` boots TRSDOS 6 and runs it, and ``trs80gp -m4 -ld prog.cmd`` LS-DOS 6.3, whose boot disk
  has too little free space there for more than a small file.
- ``z80-cpm``: a ``.com`` program for CP/M 2.2 and later, with file I/O through the BDOS. The command line comes
  from the CCP, which turns it into upper case. tnylpo (``tnylpo prog.com``) and RunCPM run it on the host; tnylpo
  works in the current directory and gives its files lower case names on the host.
- ``z80-zx``: the ZX Spectrum, as a tape file with a BASIC loader, for an emulator such as Fuse: ``LOAD ""`` loads
  and starts it. The ULA is on port ``$fe``; the screen at ``$4000`` is plain RAM. There are no files: the file routines fail.
- ``z80-c128``: the Commodore 128 with its Z80. The output is a program file without an extension that loads at
  ``$5000``: put it on a disk image (for example with VICE's ``c1541``), load it with ``LOAD"NAME",8,1`` and start
  it with ``BANK 0:SYS 20480``. Its first code runs on the 8502: it puts a jump to the Z80 code at ``$FFEE`` and
  switches to the Z80, which returns to BASIC when the program ends. zcc also writes a ``.ldr`` BASIC loader, which
  loads the program under the name it was linked as. The console is z88dk's ANSI terminal on the 40 column screen
  (see the z88dk-ansi textio above), which z88dk moves to ``$2000``; back in BASIC the screen at ``$0400`` returns and the program's output is gone, so
  a program whose output should stay readable waits for a key before it ends. On the Z80 the VIC, SID and CIAs are I/O ports, so a
  Prog8 ``@($d020)`` or a memory-mapped variable at a chip's address writes RAM, not the chip. There are no files: the file routines fail.

The ZX Spectrum and the C128 reach their hardware only through I/O ports, which Prog8 code can't access yet.

.. _llvm16_6809:

The 6809 with llvm-mc6809
^^^^^^^^^^^^^^^^^^^^^^^^^

The built-in ``mc6809-sim`` profile (``-target llvm16 -triple mc6809-sim``) builds a bare-metal 6809 program with the
``mc6809-clang`` of the `llvm-mc6809 <https://github.com/markrvmurray/llvm-mc6809>`_ release bundle, which includes the
picolibc C library; ``LLVM_MC6809`` names its directory. As with the other llvm16 profiles, writing the ``.ll`` file
works without it. The program is linked with ``-mcrt0=semihost``, the startup code for a simulator, and ``-emu`` runs
it in ``usim09batch``, which prints the program's output, reads its input and gives back its exit status. Build
``usim09batch`` from Mark Murray's USim fork (``markrvmurray/usim``, not the original USim) at the revision that
llvm-mc6809's CI pins, and put it on the PATH; it builds on Unix-like systems only. The run command stops a program after
2 billion instructions, and ``usim09batch`` then exits with status 124. The profile also links a small support source
that waits for the simulated console to send the last character before the program halts, which the simulator would
otherwise lose.

Everything listed above for ``llvm16`` applies, with ``io_ranges`` of ``$ffc0-$ffcf``, the simulator's devices. Besides:

- both 6809 profiles build static code (``-fno-pic`` in ``clang_args``): the program loads at a fixed address, so
  static variables are addressed with 3-byte extended addressing instead of 4-byte PC-relative addressing, which made
  p8vi's gap buffer test 4.4% smaller (a very small program can come out a few bytes larger).

- the 6809 is big-endian, and so are the program's words, longs and quads in memory: ``peekw``, ``pokew``, word
  arrays, struct fields and byte views of words, such as ``@(&w)`` and ``@(&w+1)``, follow the machine's byte order:
  ``@(&w)`` is the most significant byte here. Use ``lsb``, ``msb``, ``setlsb``, ``setmsb`` and ``mkword`` for code that
  must give the same result on every target.
- the cx16 virtual registers keep their meaning: ``cx16.r0L`` is still the low byte of ``cx16.r0``, which on a
  big-endian target lies at the register's address + 1. The two words of each pair such as ``cx16.r0r1sl`` are
  swapped as well, so that ``cx16.r0`` stays the low word of the long; so the addresses of ``cx16.r0`` to ``cx16.r15``
  are not ascending.
- the 2-byte header that ``diskio.save`` writes, and that ``diskio.load`` skips, keeps the low byte of the address
  first, as in a Commodore ``.prg`` file.
- console input works, through picolibc's ``getchar``.
- there are no files: ``fopen`` links but always fails, so the file routines report a failure. Directories,
  ``curdir()`` and waiting behave as on ``mos-sim``. picolibc is built without floats, and has no math library
  routines, ``strtod`` or ``usleep``.

The built-in ``mc6809-coco`` profile (``-target llvm16 -triple mc6809-coco``) builds a program for the Color Computer 2
and 3 with Extended or Disk Extended Color BASIC, with the ``clang`` of the same release bundle for the
``mc6809-unknown-decb`` triple. ``-o name`` gives ``name.bin``, a machine language file for ``LOADM``: the program and its
direct page load at ``$3F00``. Nothing here runs it, so ``-emu`` doesn't work. Copy the file to a Disk BASIC disk image,
for example with the ToolShed tools: ``decb dskini disk.dsk`` makes an empty one, and
``decb copy -2 -b name.bin disk.dsk,NAME.BIN`` copies the program to it. Then on the CoCo, or in an
emulator such as XRoar (``xroar -machine coco3 -load-fd0 disk.dsk``, or ``-machine coco2bus`` for a CoCo 2), type::

    CLEAR 200,&H3EFF
    LOADM"NAME"
    EXEC

The ``CLEAR`` moves BASIC's strings and stack below the program; without it the program gets no memory for
``malloc``. The program, its data and its heap share the memory from ``$3F00`` to the top of RAM, ``$7FFF`` in BASIC on
a 32 KB or 64 KB machine and on the CoCo 3, so about 16 KB.

A larger program can load lower, at the start of any page: ``%address $2500`` in the main module, or ``-address $2500``
on the command line, which takes the place of the directive, so that the same source can also be built for other
targets. The direct page is the first page of the program, and ``EXEC`` starts it one page further, at ``$2600``.
The ``CLEAR`` then gives the address just below the program, ``CLEAR 200,&H24FF``, and BASIC's program and variables
must end below it: Disk Extended Color BASIC puts the BASIC program after its 4 graphics pages, at ``$2601``, so
``PCLEAR 1`` first moves it down to ``$1401`` (``PRINT PEEK(25)*256+PEEK(26)`` shows where it starts).
Loaded at ``$2500``, the program has about 23 KB. When the program ends it returns to BASIC, without an exit
status. XRoar's ``-run`` and ``-load`` options start a ``.bin`` before BASIC has set up the machine, which doesn't work.

Everything listed above for ``mc6809-sim`` applies, apart from these:

- every constant address is volatile (``io_ranges = *``), as on the other machine profiles: the hardware is at
  ``$FF00-$FFFF``, and BASIC's interrupt changes variables in RAM.
- the console goes through the BASIC ROM, to the 32x16 text screen at ``$0400``, and input reads the keyboard.
  The screen has no lower case: BASIC shows lower case letters as inverse upper case ones. The profile's
  ``library = coco`` gives ``txt`` the coco textio for that screen (the CoCo 3's 40 and 80 column screens and graphics
  modes are not used):

  - output goes to BASIC's ``CHROUT`` unbuffered, through the profile's ``putchar_symbol``, a small C routine embedded
    in the compiler that turns ``\n`` into the carriage return that ``CHROUT`` wants. ``CHROUT`` handles carriage return
    and backspace, scrolls at the end of the screen, and ignores the other control codes (line feed, 7, 9, 12, 27, ...).
  - ``txt.width()`` and ``txt.height()`` give 32 and 16. ``txt.cls()`` fills the screen with spaces;
    ``txt.plot()``, ``txt.home()`` and ``txt.column()`` set BASIC's cursor ``CURPOS`` (``$0088``, the screen address
    where ``CHROUT`` prints next, ``txt.CURPOS``), so they also move where BASIC prints after the program.
  - ``txt.setchr()`` and ``txt.getchr()`` use screen memory (``txt.SCREEN``), converting between ASCII and the VDG's
    codes: ``@`` to ``_`` are ``$40-$5F``, space to ``?`` ``$60-$7F``, and lower case is inverse upper case
    ``$00-$1F``, as BASIC prints it. 128-255 are the graphics blocks, unchanged; ``setchr`` shows 0-31 as 64-95.
    ``getchr`` gives the character that ``setchr`` put there, inverse letters as lower case and the other inverse
    characters (``$20-$3F``) as their normal ones; 255 off the screen.
  - reverse video: ``txt.rvs_on()`` sets ``txt.inverse_mode`` to 128 and ``txt.rvs_off()`` back to 0. While it is set,
    ``txt.chrout()`` (and so ``txt.print()``) makes each character from 32 to 127 inverse in screen memory after
    ``CHROUT`` has printed it, which also works when the character scrolled the screen.
  - there are no colors: VDG text has no per-character colors, so ``txt.color()`` and ``txt.setclr()`` do nothing, and
    ``txt.setcc()`` and ``txt.fill_screen()`` ignore the color. ``txt.bell()`` does nothing.
  - input goes through picolibc's ``getchar``, which waits for a key and doesn't echo it; ``txt.input_line()`` echoes
    what it reads, with backspace (the left arrow) removing the last character. ``txt.getkey()`` and ``txt.waitkey()``
    read the keyboard without waiting and waiting (see "Keyboard input on llvm16" above). ``DEFAULT_WIDTH`` and
    ``DEFAULT_HEIGHT`` are the screen's 32 and 16.
- ``sys.wait()`` waits that many ticks of BASIC's 60 Hz ``TIMER`` (``$0112``), which its interrupt counts at each
  vertical sync, halting the CPU with ``SYNC`` until each interrupt; ``sys.waitvsync()`` waits for the next one, so it
  really waits for the vertical sync. The profile's startup source gives them a ``usleep``, which picolibc lacks.
  While IRQs are masked (``sys.set_irqd()``) the timer stops, and both return at once.
- there are no files: picolibc for DECB has no ``open`` or ``unlink``, and as on ``mos-sim`` the file routines
  report a failure. There is no command line, and no floats or math library routines.


Memory Model
============
.. index:: single: Targets; Memory model

.. _pointer_size:

Pointer size
------------
The size of a pointer (memory address) depends on the target's CPU architecture:

- **6502-family targets** (c64, cx16, c128, pet32): **2 bytes** (16-bit address space, 64 KB)
- **m68k targets** (amiga500, amiga1200, qemu68k): **4 bytes** (32-bit pointers; available memory depends on the target)
- **virtual target**: **4 bytes** (32-bit pointers, 16 MB modeled memory)
- **llvm64 target**: **8 bytes** (the 64-bit address space of the host)
- **llvm32 target**: **4 bytes** (32-bit platforms such as wasm32)
- **llvm16 target**: **2 bytes** (16-bit platforms: the 6502 with llvm-mos, the Z80 with llvm-z80, the 6809 with llvm-mc6809)

The ``pointer`` type keyword automatically takes the correct size for the target,
making it the natural choice for variables that hold a memory address in portable code.
On 6502 targets it is equivalent to ``uword``; on m68k and virtual targets it is equivalent to ``long``;
on the llvm64 target it is equivalent to ``uquad``, on the llvm32 target to ``long``, and on the llvm16 target to ``uword``.
Amiga hardware has a 24-bit physical address space, while the ``qemu68k`` target is configured for
1 MB of RAM. A 32-bit pointer does not imply that the target has a full 4 GB of memory.
Alternatively, you can use ``uword``, ``long`` or ``uquad`` directly if you know the target in advance.

On llvm64 a *constant* address is limited to 32 bits for now: a memory-mapped variable, ``@(...)`` and ``goto`` at a fixed
address, and a constant cast to a pointer type, must stay at or below ``$ffff_ffff``. Addresses computed at run time, and
64-bit constants stored into a ``pointer`` or ``uquad`` variable, use all 64 bits.

Generic 6502 Physical address space layout
------------------------------------------

The 6502 CPU can address 64 kilobytes of memory at a time.
Most of this address space can be used by Prog8 programs. Some built-in targets support
target-specific banked calls; see :ref:`banking`. This is not a portable abstraction for arbitrary
RAM expansions or banks.

======================  ==================  ========
memory area             type                note
======================  ==================  ========
``$00``--``$ff``        zeropage            contains many sensitive system variables
``$100``--``$1ff``      Hardware stack      used by the CPU, normally not accessed directly
``$0200``--``$ffff``    Free RAM or ROM     free to use memory area, often a mix of RAM and ROM
                                            depending on the specific computer system
======================  ==================  ========

Footnotes for the Commander X16

*Golden Ram $0400 - $07FF*
    *free to use.*

*Zero Page $0000 - $00FF*
    $00 and $01 are hardwired as Rom and Ram banking registers.

    $02 - $21 are the 16 virtual cx16 registers R0-R15.
    Note: these virtual registers are not automatically initialized to zero at program startup.

    $22 - $7F are used by Prog8 to put variables in.

    The top half of the ZP ($80-$FF) is reserved for use by the Kernal and Basic in normal operation.
    Zero page use by Prog8 can be manipulated with the ``%zeropage`` directive, various options
    may free up more locations for use by Prog8 or to reserve them for other things.


Footnotes for the Commodore 64
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
.. index:: single: Targets; Commodore 64 notes

*Program RAM $C000-$CFFF*
    *free to use:* $C000 - $CFDF
    *reserved:* $CFE0 - $CFFF for the 16 virtual cx16 registers R0-R15

*Program RAM / BASIC ROM $A000-$BFFF*
    On the C64 the Basic ROM normally occupies this memory area. However Prog8 programs that do not
    use floating point variables, actually bank out the Basic ROM to reclaim the 8 Kb of RAM that
    is hidden below it. This means that all the memory from $0801 to $D000 (exclusive) is available

*Zero Page $0000 - $00FF*
    Consider the full zero page to be reserved for use by the Kernal and Basic in normal operation.
    Zero page use by Prog8 can be manipulated with the ``%zeropage`` directive, various options

Footnotes for the Amiga targets
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
.. _amiga500footnotes:
.. index:: single: Targets; Amiga 500 notes

The amiga500 and amiga1200 targets use the M68k code generator
backend and produce Amiga Hunk executable files via the vasm assembler.
The amiga500 targets a plain 68000 CPU (upgraded to 68020 for the assembler when floats are used);
the amiga1200 targets a 68020 CPU (which enables some extra instructions) and is always assembled
with ``-m68020 -m68881``. That flag only enables assembling FPU instructions: a program that does
not use floats still runs on a stock Amiga 1200 without an FPU. Everything else in this
section applies to both.

Unlike the 6502 targets, the 68000/68020 CPU is **big endian**: multi-byte values (words, 32-bit longs and
pointers) are stored Most Significant Byte first in memory. See :ref:`pointer_size` and
:ref:`the endianness notes <endianness>` in the variables chapter.

The ``-emu`` flag launches **Copperline** (https://copperline.dev/), running the compiled program
directly via its ``--run`` option with warp boot. Copperline bundles an AROS Kickstart replacement, so
no ROM or Workbench installation is required by default. If a suitable Kickstart ROM is found in
``Documents/FS-UAE/Kickstarts`` (v1.3 for amiga500, v3.1 for amiga1200), it is used instead.
The staging directory (``<tmp>/prog8-copperline-<model>``) is populated from
``Documents/FS-UAE/Hard Drives/Harddisk500`` or ``Harddisk1200`` (system libraries mostly).

The ``-emu2`` flag uses **Vamos** from the `Amitools <https://github.com/cnvogelg/amitools>`_ package
to run the compiled program. Vamos is a very limited Amiga runtime that runs on the host operating system
directly - it is **not** a full Amiga emulator. Many AmigaOS library calls and features are not supported
or behave differently. For best results, copy the generated executable to a proper Amiga emulator such as
`WinUAE <https://www.winuae.net/>`_ or `FS-UAE <https://fs-uae.net/>`_ and run it there instead.

Blocks can opt-in to living in Amiga CHIP RAM via the ``%option amiga_chipram`` block-level option;
see the :ref:`directives` for details on the ``%option`` directive.

**Command-line arguments:**
When a program is launched from the Amiga CLI (shell), command-line arguments are available via
``sys.arguments``. This is a pointer to a null-terminated string containing the arguments. If the
program is launched from Workbench (GUI), ``sys.arguments`` is NULL. Example::

    %import textio
    main {
        sub start() {
            if sys.arguments != 0 {
                txt.print("Arguments: ")
                txt.print(sys.arguments)
                txt.print("\n")
            } else {
                txt.print("Launched from Workbench\n")
            }
        }
    }

Note: Do not use ``%option no_sysinit`` on amiga500/amiga1200 programs that need CLI argument handling,
as the startup code is required to capture and process the arguments.

**Icon library and Tooltypes:**
Amiga programs launched from Workbench don't have an arguments string, but they can read
configuration from their icon's Tooltypes using the ``icon`` module. Tooltypes are stored in the program's .info file and can be
accessed via ``icon.GetDiskObject()``, ``icon.FindToolType()``, and ``icon.MatchToolValue()``.
Note: Check that ``sys.IconBase`` is non-zero before using icon functions.


Zero page usage by the Prog8 compiler
-------------------------------------
.. index:: single: Targets; Zero page usage

Prog8 knows what addresses are safe to use in the various ZP handling configurations.
It will use the free ZP addresses to place its ZP variables in,
until they're all used up. If instructed to output a program that takes over the entire
machine, (almost) all of the ZP addresses are suddenly available and will be used.

**zeropage handling is configurable:**
There's a global program directive to specify the way the compiler
treats the ZP for the program. The default is to be reasonably restrictive to use the
part of the ZP that is not used by the C64's Kernal routines.
It's possible to claim the whole ZP as well (by disabling the operating system or Kernal).
If you want, it's also possible to be more restrictive and stay clear of the addresses used by BASIC routines too.
This allows the program to exit cleanly back to a BASIC ready prompt - something that is not possible in the other modes.


IRQs and the zeropage
^^^^^^^^^^^^^^^^^^^^^

The normal IRQ routine in the C64's Kernal will read and write several addresses in the ZP
(such as the system's software jiffy clock which sits in ``$a0 - $a2``):

``$a0 - $a2``; ``$91``; ``$c0``; ``$c5``; ``$cb``; ``$f5 - $f6``

These addresses will *never* be used by the compiler for ZP variables, so variables will
not interfere with the IRQ routine and vice versa. This is true for the normal ZP mode but also
for the mode where the whole system and ZP have been taken over.
So the normal IRQ vector can still run and will be when the program is started!




CPU
===

Directly Accessible Registers
-----------------------------
.. index:: single: Targets; CPU Registers

The hardware CPU registers (A, X, Y on 6502; D0-D7, A0-A7 on m68k) are not directly accessible from regular Prog8 code.
If you need to work with them, you'll have to use some inline assembly with ``%asm``.
Or, if they are required to have a value as arguments to some external kernal or library assembly routine,
just use a normal subroutine call to an ``extsub`` that correctly specifies what registers go where.
The compiler will then take care of loading the arguments into the required registers and returning
any response value(s) back to the prog8 code.

The CPU status register (P on 6502; CCR/SR on m68k) carry flag and interrupt disable flag *can* be written via a couple of special
builtin functions (``set_carry()``, ``clear_carry()``, ``set_irqd()``,  ``clear_irqd()``),
and read via the ``read_flags()`` function.  With the special status branch statements like ``if_cc``,
``if_cs`` etc you can branch directly on the status of the flags.

.. note::
   On M68k targets, ``set_carry()`` and ``clear_carry()`` also affect the X (extend) flag,
   because the rotate instructions (``rol``, ``ror``) use the X bit as the rotate-carry
   rather than the C bit that is used for comparisons.  ``set_carry``/``clear_carry`` manage
   both bits to keep them in sync.  On 6502-based targets there is a single carry flag and
   this distinction does not arise.

The 16 'virtual' 16-bit registers that are defined on the Commander X16 machine are not real hardware
registers and are just 16 memory-mapped word values that you *can* access directly from everywhere.


IRQ Handling (general)
======================
.. index:: single: Targets; IRQ Handling

The IRQ facilities described here apply to the CBM 6502-based targets (c64, c128, pet32, cx16) only.
The m68k targets do not provide them: the amiga500 and amiga1200 have none of these routines (interrupt handling
there is done via the AmigaOS, which is out of scope for these convenience routines) and the qemu68k
simulator only offers the interrupt disable/enable helpers.

Normally, the system's default IRQ handling is not interfered with.
You can however install your own IRQ handler (for clean separation, it is advised to define it inside its own block).

High-level convenience routines
-------------------------------

On the C64, C128, PET32 and CommanderX16 targets there are a few library routines available to make setting up
60hz/vsync IRQs a lot easier (no assembly code required).
These routines are::

    sys.set_irq(uword handler_address)
    sys.restore_irq()          ; set everything back to the systems default irq handler
    sys.set_rasterirq(uword handler_address, uword rasterline)    (not on PET32)
    sys.update_rasterirq(uword handler_address, uword rasterline) (not on PET32)
    sys.set_rasterline(uword rasterline)                          (not on PET32)

The IRQ handler routine must return a boolean value (0 or 1) in the A register:
0 means do *not* run the system IRQ handler routine afterwards, 1 means run the system IRQ handler routine afterwards.

.. note::
    The PET32 target only supports ``sys.set_irq()`` and ``sys.restore_irq()``.
    The raster-related routines are not available on PET32.


Low-level bare IRQ handler
--------------------------

Some targets allow you to install a "bare" IRQ handler directly into the system's interrupt vector,
bypassing the high-level ``sys.set_irq()`` convenience routines. A bare handler is just a subroutine
that is called directly by the CPU on each interrupt -- there is no register-saving wrapper around it.

On Commodore targets (C64, C128, PET32, Commander X16) you install such a handler by writing to the
``cbm.CINV`` RAM vector::

    uword saved_irq = cbm.CINV    ; save old handler address (may be $0000 if none)

    sys.set_irqd()
    cbm.CINV = &my_handler        ; install our handler
    sys.clear_irqd()

Other targets may use a different vector or may not support bare handlers at all.

.. caution::
    On Commodore targets, the KERNAL saves A, X, Y before dispatching through the CINV vector,
    so a bare handler does not need to save/restore them. However, the handler **must** save
    and restore the compiler's internal zero-page scratch registers via
    ``sys.save_prog8_internals()`` / ``sys.restore_prog8_internals()`` — the KERNAL does not know
    about those, and the handler's own Prog8 code may corrupt them.

    The handler must also chain to the previous handler to preserve system services
    (jiffy clock, keyboard scan, cursor blink). A correct bare handler on Commodore looks like this::

        uword saved_irq

        sub my_handler() {
            sys.save_prog8_internals()

            ; ... your IRQ handler code here ...

            sys.restore_prog8_internals()
            goto saved_irq      ; chain to previous handler
        }

    Make sure to declare ``saved_irq`` as a ``uword`` variable in the same scope, and save the
    current value of the interrupt vector into it before overwriting it.

.. caution::
    Be cautious about calling ROM routines within an interrupt handler. Some kernal routines are fine to call,
    others can be problematic. The safest approach is just to modify a flag variable in the handler and act on that
    flag in the regular main loop of the program (i.e. call the required kernal routines there, and then reset the flag).

.. caution::
    It is advised to **not use floating point calculations** inside IRQ handler routines.
    They are very slow, and the correct ROM bank must be enabled to call them. Make sure the correct
    ROM bank is reset at the end of the handler as well.
    There is also the possibility of corrupting variables and floating point calculations
    that are being executed in the interrupted main program. These memory locations should be
    backed up and restored at the end of the handler, further increasing its execution time...

.. caution::
    The Commander X16's sixteen 'virtual registers' R0-R15 *are not preserved* in the IRQ handler! (On any system!)
    So you should make sure that the handler routine does NOT use these registers, or do some sort of saving/restoring yourself
    of the ones that you do need in the IRQ handler.  Prog8 itself may also use these registers, so be very careful.
    This is not a X16 specific thing; these registers also exist on the other compiler targets, and the same
    issue holds there.

    There are two utility routines in cx16 that save and restore *all* 16 registers. It's a bit inefficient if
    only a few are clobbered, but it's easy to put calls to them into your IRQ handler routine at the start and end.
    These routines are ``cx16.save_virtual_registers()`` and ``cx16.restore_virtual_registers()``.


.. _x16-specific-irq:

Commander X16 specific IRQ handling
===================================
.. index:: single: Targets; Commander X16 IRQ Handling

Be careful: for the CommanderX16, set_rasterirq() will disable VSYNC irqs and never call the system IRQ handler regardless
of the return value of the user handler routine. This also means the default sys.wait() routine won't work anymore,
when using this handler.

These two helper routines are not particularly suited to handle multiple IRQ sources on the Commander X16.
It's possible but it requires correct fiddling with IRQ enable bits, acknowledging the IRQs, and properly calling
or not calling the system IRQ handler routine. See the paragraph below for perhaps a better and easier solution that
is tailored to this system.

.. caution::
    **When Using VERA in the handler:**
    The Commander X16 syslib provides some additional routines that should be used *in your IRQ handler routine* if it uses the Vera registers.
    They take care of saving and restoring the Vera state of the interrupted main program, otherwise the IRQ handler's manipulation
    will corrupt any Vera operations that were going on in the main program. The routines are::

        cx16.save_vera_context()
        ; perhaps also cx16.save_virtual_registers() here... see caution below
        ; ... do your work that uses vera here!...
        ; perhaps also cx16.restore_virtual_registers() here... see caution below
        cx16.restore_vera_context()


**Multi-IRQ support routines**

Instead of using the routines in ``sys`` as mentioned above (that are more or less portable
across the C64,C128 and cx16), you can also use the special routines made for the Commander X16,
in ``cx16``. The idea is to let Prog8 do the irq dispatching and housekeeping for you, and that
your program only has to register the specific handlers for the specific IRQ sources that you want to handle.
*All cautions mentioned above, regarding the VERA and Virtual registers, floating point and kernal routines, still apply!*

Look at the examples/cx16/multi-irq-new.p8 example to see how these routines can be used.
Here they are, all available in ``cx16``:

``disable_irqs ()``
    Disables all Vera IRQ sources. The CPU irq disable flag is not changed by this routine;
    you can manipulate that via ``sys.set_irqd()`` and ``sys.clear_irqd()`` as usual.

``enable_irq_handlers (bool disable_all_irq_sources)``
    Install the "master IRQ handler" that will dispatch IRQs to the registered handler for each type.
    Only Vera IRQs supported for now.
    Pass true to initially disable all Vera interrupt sources (they will be enabled individually again
    by setting the various handlers), or pass false to not touch this.
    The handlers don't need to clear its ISR bit, but have to return 0 or 1 in A,
    where 1 means: continue with the system IRQ handler, 0 means: don't call that.
    The order in which the handlers are invoked if multiple interrupts occur simultaneously is: LINE, TIMER1(VIA1), VSYNC, SPRCOL, AFLOW.

``set_vsync_irq_handler (uword address)``
    Sets the vertical sync interrupt handler routine.  Also enables VSYNC interrupts.

``set_line_irq_handler (uword rasterline, uword address)``
    Sets the rasterline interrupt handler routine to trigger on the specified raster line.
    Also enables LINE interrupts.
    You can use ``sys.set_rasterline()`` later to adjust the rasterline on which to trigger.

``set_sprcol_irq_handler (uword address)``
    Sets the sprite collision interrupt handler routine.  Also enables SPRCOL interrupts.

``set_aflow_irq_handler (uword address)``
    Sets the audio buffer underrun interrupt handler routine.  Also enables AFLOW interrupts.
    Note: the handler must fill the Vera's audio fifo buffer by itself with at least 25% worth of data (1 kb)
    otherwise the aflow irq keeps triggering.

``set_timer1_irq_handler (uword address)``
    Sets the VIA1 TIMER1 irq handler to use with enable_irq_handlers().  Does not enable or disable VIA1 timer irqs setting.

``disable_irq_handlers ()``
    Hand control back to the system default IRQ handler.

And a utility method to set the VIA1 timer1 to trigger IRQs at regular intervals:

``sub set_timer1 (uword delay, bool keeprunning)``
    Set VIA1 timer1 to trigger after the given delay (cycles).
    Enables VIA timer1 irqs if delay>0, otherwise disables it.
    If keeprunning then the timer keeps triggering, otherwise it stops after a single trigger.
    The speed of the timer depends on the clock speed of the X16 (controlled by a jumper on the motherboard, usually 8 MHz).
